\section{Evaluation Aim}

The validation methodology is designed to test the thesis claim at the architectural level: a robot-facing LLM planner is useful only if its plans remain grounded in the live ROS4HRI state, respect the available skill contracts, expose execution failures through typed feedback, and produce user-facing dialogue through the intended speech owner. The evaluation therefore does not treat success as a single demonstration outcome. It treats success as a combination of route correctness, plan validity, execution validation, recovery behaviour, and traceability.

The strategy separates four evidence layers so that a success in one layer cannot conceal a failure in another. First, controlled planner-request probes use fixed grounded context to isolate schema compliance, skill selection, plan lineage, and orchestrator dispatch from speech and dialogue timing. Second, the thesis-facing questionnaire injects complete user turns through the ROS4HRI speech path in the canonical \code{response_first} profile; this is the main full-stack score because it covers routing, planner handoff, execution feedback, and exactly-once speech. Third, named environment fixtures preload deterministic KnowledgeCore and scene state so that grounding-sensitive cases can be repeated. Fourth, a separate multi-step deterministic fake-skill policy ladder injects staged skill outcomes to test success, recoverable failure, ambiguity, and replan behaviour without depending on physical hardware. The \code{intent_first} mode and a detector-enabled launch are reported as ablation and perception profiles respectively, not merged into the baseline score.

\section{Fake-Skill Scenario Validation}

The fake-skill suite is the deterministic substrate for recovery testing. It avoids the main weakness of prompt-only simulation: the planner and orchestrator still interact with ROS actions that return typed payloads, emit \code{/fake_skills/events}, and can update controlled scenario state. The package supports global modes such as \code{scenario}, \code{always_success}, \code{always_fail}, \code{every_other}, and \code{random_seeded}, together with named or dynamic policies that fail a selected navigation, search, manipulation, delivery, or recipient-resolution stage.

The scenario suite is organised around case families rather than isolated commands. This makes it possible to compare planner behaviour under different outcome policies while keeping the user goal fixed.

\section{Multi-Step Deterministic Fake-Skill Scenarios}

These scenarios combine multi-step fake execution, structured fixture state, deterministic failure injection, and trace-level evidence. They are important because many planning failures only appear after the first step has succeeded and the stack must decide whether to continue, replan, ask the user, or stop.

The deep suite uses a policy ladder over representative multi-step goals:

\begin{enumerate}
  \item \textbf{All-success baseline.} Every planned step succeeds. The expected trace contains ordered, non-duplicated dispatch, complete lineage, one terminal state, and one final user-facing report.
  \item \textbf{Fail-once navigation.} The first relevant navigation step fails recoverably and a later attempt may succeed. The planner must preserve completed work, issue a newer plan version when replanning, and avoid replaying unrelated steps.
  \item \textbf{Fail-once manipulation.} A pick or placement stage fails after earlier movement or search has succeeded. The response must not claim delivery, and any retry must remain tied to the same goal with stable step lineage where applicable.
  \item \textbf{Blocked delivery or missing recipient.} A required path, object, or recipient cannot be resolved. The expected outcome is clarification or truthful safe termination rather than an invented substitute or false completion.
  \item \textbf{Seeded stress profile.} After deterministic policies pass, \code{random_seeded} explores additional outcome combinations while retaining an exact seed and event trace for reproduction.
\end{enumerate}

\section{Execution Profiles}

The primary thesis-facing mode is full user-turn injection through the ROS4HRI speech ingress. Before a \code{LiveSpeech} event is published, the corresponding speaker is made visible on the tracked-voices stream using reliable, transient-local delivery. Scored questionnaire cases use a group voice scope so that the dialogue stack observes the same ingress contract as a live interaction. This profile is slower than direct request injection but is the only one that jointly tests chatbot routing, planner admission, feedback relay, and speech ownership.

Planner-request injection remains a diagnostic profile. A controlled payload with fixed \code{goal_text}, normalised intents, scene targets, and \code{grounded_context} is published at the planner gate to isolate the planner, orchestrator, and selected skill server. It is useful for narrowing a failure, but it does not receive the main end-to-end score. The multi-step deterministic fake-skill score is also reported separately because it measures goal handling under controlled action outcomes rather than robot hardware performance. Finally, object-recognition cases use a distinct detector-enabled profile when the main runtime deliberately launches with object detection disabled; a missing detector process is never counted as negative detector evidence.

\section{Metrics}

For each run, the validation log records the case id, utterance, route mode, fake-skill mode, scenario id, seed, planner call status, plan steps, dispatched skills, result statuses, clarification flag, final status, final response text, timeout flag, warning count, and error count. The main aggregate metrics are:

\begin{itemize}
  \item route accuracy;
  \item valid-plan rate;
  \item expected-skill coverage;
  \item fake-skill dispatch rate;
  \item safe-failure rate;
  \item clarification rate when ambiguity is expected;
  \item timeout rate;
  \item forbidden-plan rate, especially executable \code{say} steps when speech should remain under dialogue ownership;
  \item phase-completion rate across turn injection, route observation, planner request, execution feedback, terminal state, and speech;
  \item fallback-event rate, distinguishing observed ROS evidence from timeout or log-derived inference;
  \item stale-world contamination rate across fixture changes;
  \item exactly-once acknowledgement and terminal-speech rate;
  \item replan-lineage correctness, including plan-version changes and preservation of completed work;
  \item mean and maximum latency, when timestamps are available.
\end{itemize}

\section{Evidence Bundle}

A complete validation run should produce a reproducible bundle containing the suite configuration, JSONL trace, per-case metrics, aggregate metrics, and a short report. The expected layout is:

\begin{lstlisting}[style=sharedCode, caption={Expected validation evidence bundle.}]
docs/evaluation/runs/<timestamp>/
  suite_config.yaml
  runtime_metadata.json
  environment_fixture.yaml
  trace.jsonl
  per_case_metrics.csv
  aggregate_metrics.json
  report.md
  report.html
  selected_traces/
    <case_id>_trace.json
\end{lstlisting}

Each case trace records explicit \code{phase_observations}, fallback markers, a terminal \code{plan_outcome_summary}, planning and KB evidence, and the speech events used for exactly-once assessment. Runtime metadata identifies the source revision, launch profile, model configuration, prompt-pack revisions, registry projection, fixture, and fake policy or physical adapter. The stale-world guard records whether undeclared state from an earlier case was observed. The thesis uses this structure as the evidence contract; focused probes remain diagnostic until reproduced by the declared suite and profile.
