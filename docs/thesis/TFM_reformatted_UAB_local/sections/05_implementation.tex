\chapter{Implementation: ROS Nodes and APIs}
\label{chap:implementation}
\label{sec:implementation}

This chapter describes how the architecture introduced in Chapter~\ref{chap:architecture-requirements} and the contracts defined in Chapter~\ref{chap:runtime-contracts} are realised in the ROS~2 workspace. The implementation deliberately separates semantic interpretation, planning, deterministic execution, perception grounding, symbolic knowledge, and skills. LLM components can therefore interpret or propose actions, but physical effects remain mediated by typed ROS interfaces and validated skill contracts.

The workspace combines locally developed integration packages with upstream-aligned ROS4HRI components. In particular, \code{dialogue_manager} provides a bridge between robot and user interaction, while the \code{chatbot_llm} package supplies intent extraction, response generation, and the turn-processing interface extended for this system. The planner-facing contracts, orchestrator, perception pipeline, fake-skill infrastructure, skill registry and NAO adapters are integrated in the main \code{nao-ros4hri-bridge} workspace. This distinction matters: the contribution is not a replacement dialogue framework, but a planner-mediated execution architecture fitted to existing ROS4HRI seams.

\section{Runtime Flow}

A user utterance first enters \code{dialogue_manager}, which sends a \code{DialogueInteraction} request to \code{chatbot_llm} with the dialogue state required for the turn. The chatbot combines this state with a symbolic representation of the current scene derived from the knowledge base, performs the call to the LLM for intent classification and response generation, and classifies the result as \code{dialogue}, \code{knowledge_query}, or \code{execution}. \code{dialogue} and \code{knowledge_query} turns return a response to the dialogue owner without entering the planner. \code{execution} turns additionally produce a structured planner request with goal metadata, normalised intent hints, dialogue history and current world state. This request is published to \code{/nao_orchestrator/planner_request} for admission.

Candidate requests are published to the planner-admission endpoint defined by Contract~2 (Table~\ref{tab:planner-request-fields}). This endpoint is owned by \code{nao_orchestrator}, which normalises the payload, establishes goal lineage, and forwards only admissible requests on \code{/planner/request}. \code{planner_llm} generates a structured plan from that request and the shared skill registry, including execution order, relevant KB entities such as objects, locations, and people, and the metadata required for deterministic dispatch. The resulting planner output returns to the orchestrator, where its schema, skill names, arguments, and step ordering are checked before any action or service is invoked. Step outcomes are published on \path{/planner/execution_feedback}. A goal-keyed planning-state helper inside \code{planner_llm} consumes this feedback when the orchestrator reports a relevant event, such as a failed step, a clarification requirement, or a recoverable condition. It updates the active planning state and may request a replan or planner dialogue act. The planner node itself does not monitor or control robot execution.

This flow enforces three runtime constraints from the requirements in Table~\ref{tab:functional-requirements}. First, a dialogue-only turn cannot reach robot execution unless the chatbot selects the execution route and the orchestrator admits the resulting request (FR2--FR3). Second, planner output remains a candidate plan until its schema, skill names, arguments, failure policies, and lineage fields pass deterministic validation (FR5). Third, KB facts supplied with a planner request describe what the system knows when planning begins. They can support target selection, but they cannot prove that a later action succeeded or that the world remained unchanged; the responsible skill must provide fresh execution evidence before completion is reported.

\section{ROS Nodes}

\subsection{\code{dialogue_manager}}

\code{dialogue_manager} is the ROS~2 lifecycle component responsible for multi-modal communication between the robot and its interlocutors. Following the ROS4HRI package design\footnote{Package source: \url{https://github.com/ieverythng/dialogue_manager}.}, it tracks concurrent conversations per person and per interaction group, preserves chronological utterance histories, and associates incoming \code{hri_msgs/LiveSpeech} streams with the relevant dialogue. Group utterances are fanned out to the corresponding personal and group histories, while prior summaries can be restored when a known interlocutor begins a new session. The node invokes the chatbot through \code{DialogueInteraction}, exposes the high-level \code{/skill/chat}, \code{/skill/ask}, and \code{/skill/say} interfaces, and realises final user-facing expressions through the configured Say sub-skill. The planner integration therefore extends an existing multi-user dialogue lifecycle rather than replacing it.

This ownership boundary is also a runtime constraint: planning and execution packages may publish structured communication requests, but they do not call the speech backend directly merely because they have produced status information. This preserves the separation between dialogue and execution introduced by FR2 and the ownership map in Table~\ref{tab:contract-map}.

Planner dialogue acts return through the same ownership boundary. \code{planner_llm} publishes structured acknowledgement, clarification, failure, or completion acts on \path{/planner/dialogue_act}; \code{nao_orchestrator} relays the admitted act on \path{/nao_orchestrator/planner_dialogue_act}; and the dialogue layer chooses the final wording and speech mechanism. This implementation of Contract~7 preserves one utterance authority per semantic event and makes duplicate acknowledgement or completion speech observable in the validation traces.

\subsection{\code{chatbot_llm}}

\code{chatbot_llm} is a lifecycle-managed semantic routing node built on the existing chatbot scaffold. Its turn callback receives a \code{DialogueInteraction} and the conversation history assembled by \code{dialogue_manager}. Before response generation or any planner handoff, it queries the KB through \code{kb_skills}, reads the most recent \code{/scene/summary}, and passes both sources through the \code{PlannerHandoff} projection helper. The result is the compact \code{grounded_context} defined by Contract~3 (Table~\ref{tab:grounded-context-fields} and Figure~\ref{fig:grounded-context-pipeline}). It contains a bounded set of entities, locations, and task-relevant relations instead of raw detector streams or unrestricted KB rows. This is the principal KB-to-chatbot seam: the same projection informs dialogue and knowledge answers on every user turn, and is attached to Contract~2 only when the selected route produces a planner request.

The turn engine implements the route field from Contract~1 as follows:
\begin{itemize}
  \item A \code{dialogue} route covers conversational and task-discussion turns and does not publish planner work.
  \item A \code{knowledge_query} route answers from current symbolic evidence without causing a physical action. For example, ``what can you see?'' can use the current grounded context, whereas ``scan and tell me what you see'' requests fresh sensing and is eligible for execution.
  \item An \code{execution} route constructs planner-facing metadata such as goal text, request kind, normalised intent hints, and target KB entities. It publishes a candidate request to \code{/nao_orchestrator/planner_request}, but it does not create a skill sequence.
\end{itemize}
The final point implements FR3 and the admission ownership in Contract~2: \code{chatbot_llm} may propose execution, but only \code{nao_orchestrator} can admit the request and only a validated planner output can reach skill dispatch.

The canonical behavioural policy resides in \path{src/chatbot_llm/config/chat_prompt_pack.yaml}. Python builders provide structural framing and runtime context, while the chatbot sequence uses response and intent stages that share the same system prompt, route policy, skill catalogue, and grounded context. The baseline is \code{response_first}. In planner mode, the response-stage call returns the natural \code{verbal_ack} together with the route and confidence fields from Contract~1. The intent stage then defines the user intents and, for an execution route, constructs the candidate planner handoff from that staged result. The response stage therefore performs route selection as part of the same semantic decision that produces the acknowledgement; it does not create an executable plan. In the \code{intent_first} ablation, the intent stage runs first, its route is checked and locked, and the response stage generates wording under that locked route. The comparison tests whether early route commitment changes contradictions between the spoken response and planner admission. The proposed Intent--Route--Response (IRR) variant goes further by producing the three outputs atomically, but it remains a future or separately scored implementation until its trace and route-consistency behaviour are validated.

Every completed turn emits \path{/chatbot_llm/turn_trace}. The trace records the final route, intent source and confidence, grounded-context visibility, spoken acknowledgement, and whether a planner handoff was published. It therefore provides the observable link between Contract~1, Contract~2 admission, and the route-consistency evaluation in Chapter~\ref{chap:validation-methodology}.

\subsection{\code{planner_llm}}

\code{planner_llm} is the high-level planning node and contains a goal-keyed planning-state helper for feedback-driven state transitions. The helper is a subprocess-like part of the node, not an independent execution supervisor. The node subscribes to admitted \code{/planner/request} messages rather than directly consuming chatbot output. Through \code{planner_common}, each request is normalised into the canonical contract with goal metadata nested under \code{plan}. The planner prompt combines the goal text, request kind, normalized intent hints, grounded context, the shared skill-entry projection from Contract~3A, permitted step types, and the required JSON output envelope. Planner policy is maintained in \path{src/planner_llm/config/planner_prompt_pack.yaml}; the runtime builder supplies request-specific structure without duplicating that policy in Python source.

The planner prompt is assembled from the admitted request, bounded grounded entities, the skill registry fields relevant to selection and ordering, the permitted step types, and the planner output contract. The model is told which skills are available, which arguments are required, which effects are expected, which result evidence can support completion, and which failure modes may require clarification or replanning. This registry projection is the main link between the model's language-level proposal and the typed ROS execution surface.

The model response is not treated as executable until the planner engine extracts the candidate object, normalises its schema, validates required metadata and step fields, and applies one bounded repair retry when configured. Unsupported skill names, malformed arguments, invalid recovery policies, or unparseable output become typed failure or clarification outcomes. The planner records the selected output mode, including a normal model plan or one of the explicitly named deterministic fallback modes described in Section~\ref{sec:deterministic-guards}. Valid plans are published on \code{/intents} for independent orchestrator validation.

The node also subscribes to \code{/planner/execution_feedback}. The embedded planning-state helper associates relevant events with the active goal and asks the planning path to respond when the orchestrator reports completion, failure, a recoverable condition, or a need for user input. That response may be a revised plan or a structured dialogue act; it is not robot control. The planner never invokes a robot adapter and never speaks directly. Its user-facing output must cross the orchestrator relay and dialogue owner.

\subsection{Goal-Keyed Planning-State Helper}

The goal-keyed planning-state helper maintains planning state under an active \code{goal_id}; it does not monitor or control robot execution. Each accepted plan additionally carries a \code{plan_id} and monotonically meaningful \code{plan_version}; stable \code{step_id} values allow a newer version to preserve already completed work when a replan joins the same goal. Feedback from an older or unrelated version is rejected rather than being allowed to complete the current goal accidentally.

The helper distinguishes planning, replanning, waiting-for-user, completed, and failed states. Step feedback may move the goal forward, expose a recoverable condition, or produce a structured dialogue act. If a replacement plan is necessary, \code{planner_llm} creates and validates it under a newer version. \code{nao_orchestrator} never invents a local substitute plan, which preserves a single planning authority while keeping execution deterministic. The helper maintains order and lineage across these transitions; it does not supervise the robot or replace the orchestrator's execution checks.

\subsection{Skill Registry (\code{skill_common})}

The planner-facing capability model is derived from the canonical skill registry maintained by \code{skill_common}. A registry entry identifies a skill, its typed arguments, result shape, preconditions or evidence expectations, runtime availability, executor mapping, and admissible recovery behaviour. The planner selects from this reviewed skill surface instead of inventing NAOqi calls or undocumented action names. Runtime and documentation views are generated from the same source and checked together for consistency.

The runtime skill surface includes perception and reporting skills such as \code{scan}, \code{find_object}, \code{inspect_area}, and \code{report_result}; navigation and manipulation skills such as \code{navigate_to}, \code{walk_to}, \code{bring_object}, \code{pick_object}, and \code{place_object}; social and interaction skills such as \code{perform_motion}, \code{look_at}, \code{wave_greet}, and \code{ask_user}; and explicit \code{kb_add}, \code{kb_revise}, and \code{kb_remove} operations. The same skill contract can be backed by a NAO adapter, simulator, or fake-skill server, allowing planner tests to preserve the execution API while changing the physical substrate.

\subsection{\code{nao_orchestrator} and the Execution Boundary}

\code{nao_orchestrator} is the deterministic boundary between model output and robot effects. At ingress, its planner gate admits candidate requests, normalises their contract, establishes lineage, and publishes \code{/planner/request}. At egress, it consumes executable intents, validates the nested plan against the registry and step schema, and rejects stale, duplicate, or unsupported work before dispatch. This two-sided role explains why the node appears at both admission and execution positions in Figure~\ref{fig:full-stack-architecture-plate}: it is one lifecycle component enforcing two distinct boundaries, not two planning nodes.

Accepted plans are dispatched in order through ROS actions or short request/response interfaces appropriate to each skill. The orchestrator tracks active plan and step state and publishes events including plan accepted, step started, step succeeded, step failed, and plan completed on \code{/planner/execution_feedback}. These events retain \code{goal_id}, \code{plan_id}, \code{plan_version}, and \code{step_id}, making a run reconstructable and allowing the goal-keyed planning-state helper to distinguish a failure from a stale callback. Explicit symbolic mutations are routed through \code{kb_skills}; ordinary questions and implicit LLM claims cannot write directly to KnowledgeCore.

On failure, the orchestrator reports the typed result and stops or waits according to the validated policy. It does not ask an LLM for an unregistered action, create a replacement plan, or fabricate success. Likewise, it relays planner dialogue acts but does not become a second conversational policy. These restrictions keep non-deterministic reasoning upstream of a small, auditable execution surface.

\section{Deterministic Guards and Bounded Fallbacks}
\label{sec:deterministic-guards}

The normal path is model-assisted, but several deterministic guards constrain the interfaces around it. These guards implement the admission and evidence requirements in FR2, FR3, FR5, FR6, and FR7. They are deliberately narrow and observable. A fallback does not create a second hidden planner, and it cannot convert missing evidence into a successful result.

At the chatbot boundary, \code{chatbot_llm} normalizes the route produced by the response and intent stages and checks for contradictions between the route, acknowledgement, and extracted intent. A missing or contradictory response can be repaired with a constrained route decision. When planner mode is disabled, the rules path can answer supported non-execution turns; when planner mode is enabled and the language-model result cannot be repaired safely, the node returns a typed failure rather than fabricating an execution request. In the \code{intent_first} mode, the locked route is carried into response generation and execution wording is sanitized against that route. These guards enforce the route and ownership boundaries in Contracts~1 and~2.

At the planner boundary, the engine first attempts the configured model path, extracts and validates the candidate plan, and performs at most the bounded validation retry configured by the planner prompt pack. If the candidate remains invalid, the decision is marked as a planner failure or clarification. Three narrow deterministic modes are retained for cases whose scope is explicit in the source and trace: \code{rule_fallback} handles one unambiguous primitive motion or posture request without composite markers, target ambiguity, or a requested report; \code{grounded_location_group_fallback} handles a grounded request to bring every object in a known location to a known recipient or destination and creates one delivery step per grounded object; and \code{grounded_look_fallback} handles a grounded look-at or gaze request, optionally followed by evidence-based reporting. Each mode is recorded in the planner decision metadata and remains subject to Contract~4 validation. Composite or target-ambiguous language is not silently reduced to an incomplete plan.

At the execution boundary, \code{nao_orchestrator} applies deterministic skill aliases, argument checks, lineage checks, stale or duplicate-event guards, and the selected failure policy before dispatch. Its \code{report_result} path derives the final summary from successful result payloads or trace evidence, so the planner cannot predeclare an effect that the skill did not observe. Profile-dependent adapter fallbacks, such as real versus fake motion endpoints, remain execution configuration and do not change planner policy. Feedback is published through Contract~5, and any clarification or completion request crosses Contract~6 and the dialogue owner before speech.

\section{Grounding and Knowledge}

\code{nao_scene_grounding} converts detector output into a provider-independent scene representation. It normalises labels and confidence fields, separates people from objects, maintains local object identifiers under configured matching and recency rules, and publishes the current \code{/scene/summary}. Detector-derived facts may be mirrored as transient KnowledgeCore updates through \code{/kb/revise}, but the grounding node does not become a general world model. The detector profile can currently use the established perception backend, while its public summary prevents chatbot and planner packages from depending on provider-specific messages.

\code{kb_skills} is the transport boundary for \code{/kb/query} and \code{/kb/revise}. The chatbot obtains a bounded knowledge snapshot through this interface and combines it with the current scene summary to produce \code{grounded_context}. This projection deliberately omits unrestricted raw evidence and keeps entities, locations, and relations within prompt-size bounds. Image-plane centres are retained as image evidence but are not interpreted as metric distance. Metric position or proximity requires a frame-qualified spatial overlay or fresh evidence from the responsible skill.

Planning context and execution evidence consequently have different roles. Current symbolic state is sufficient for a non-mutating knowledge answer and useful for selecting a plan. It is not sufficient to claim that an object was found after a scan, that a path remains clear, or that a manipulation succeeded. Skills that own those effects requery the relevant detector, robot, or KB seam at execution time and place the resulting evidence in their typed payload. This preserves truthful reporting when the world changes between planning and execution.

\section{Fake Skills and Simulation Seams}

The \code{fake_skills} package implements the same action-facing contracts as the runtime skill surface while replacing hardware outcomes with controlled policies. Supported global modes include \code{scenario}, \code{always_success}, \code{always_fail}, \code{every_other}, and seeded pseudo-random execution. Named scenario and dynamic policy profiles can inject a failure at a particular stage, preserve scenario state across steps, and expose recoverability information. Results carry \code{metadata.fake=true}, and \code{/fake_skills/events} records dispatch and outcome evidence for later reconstruction.

This seam permits multi-step planner and orchestrator behaviour to be exercised without conflating software feedback handling with robot reliability. The all-success profile checks plan coverage and ordered dispatch; fail-once navigation or manipulation profiles check feedback, replan lineage, and non-repetition of completed steps; blocked-delivery and missing-recipient profiles check clarification or safe termination. KB guards and post-effects allow the scenario state to change in response to a successful fake action rather than being encoded only in prose.

The resulting evidence is intentionally qualified. A fake-skill pass supports claims about routing, plan validity, deterministic dispatch, feedback handling, and recovery policy. It does not demonstrate physical navigation accuracy, grasp success, detector quality, NAOqi timing, or human-robot safety. Chapter~\ref{chap:validation-methodology} therefore reports the multi-step deterministic fake-skill score separately from the main speech-ingress stack and identifies robot- or detector-dependent checks explicitly.

\section{Models and Runtime Configuration}

The integrated launch profiles in \code{nao_chatbot} select dialogue, chatbot, planner, grounding, orchestration, skill, and adapter components as a coherent runtime. Chatbot and planner backends are independently configurable through launch parameters and environment-backed provider settings; the current stack supports local or OpenAI-compatible model endpoints without embedding credentials or host-specific addresses in source. The exact model identifier, endpoint class, temperature, timeout, prompt-pack revision, and response mode are captured with each scored validation run because they affect latency and structured-output reliability.

The prompt packs and skill registry are runtime-critical configuration, not informal documentation. The chatbot prompt pack defines response and routing policy; the planner prompt pack defines planning policy and output requirements; and the canonical skill registry defines the admissible capability surface. Changes to prompt wording are evaluated through the bounded SkillOpt process with a baseline, mutation batch, holdout checks, and an accept or reject decision. This prevents a favourable single example from silently changing behaviour at unrelated dialogue, KB, execution, report, or speech-ownership seams.

For reproducibility, final validation records whether \code{response_first} or the \code{intent_first} ablation was active, whether grounded-context digesting was enabled, which environment fixture was preloaded, which fake policy or real adapter profile was used, and whether object detection was launched. Local inference removes external quota dependence but still requires model and hardware metadata; hosted inference requires the same metadata plus endpoint and quota conditions. These run-level facts are part of the evidence bundle defined in Chapter~\ref{chap:validation-methodology}, rather than being assumed from a developer's shell configuration.
