\chapter{Implementation: ROS Nodes and APIs}
\label{chap:implementation}
\label{sec:implementation}

This chapter describes how the architecture introduced in Chapter~\ref{chap:architecture-requirements} and the contracts defined in Chapter~\ref{chap:runtime-contracts} are realised in the ROS~2 workspace. The implementation deliberately separates semantic interpretation, planning, deterministic execution, perception grounding, symbolic knowledge, and speech. LLM components can therefore interpret or propose actions, but physical effects remain mediated by typed ROS interfaces and validated skill contracts.

The workspace combines locally developed integration packages with upstream-aligned ROS4HRI components. In particular, \code{dialogue_manager} provides the established interaction lifecycle, while the nested \code{chatbot_llm} package supplies the lifecycle scaffold and turn-processing interface extended for this system. The planner-facing contracts, goal supervisor, orchestrator, grounding utilities, fake-skill infrastructure, and NAO adapters are integrated in the main \code{nao-ros4hri-bridge} workspace. This distinction matters: the contribution is not a replacement dialogue framework, but a planner-mediated execution architecture fitted to existing ROS4HRI seams.

\section{Runtime Flow}

A user utterance first enters \code{dialogue_manager}, which sends a \code{DialogueInteraction} request to \code{chatbot_llm} with the dialogue state required for the turn. The chatbot combines this state with a bounded projection of the current scene and knowledge base, calls its configured language-model backend, and classifies the result as \code{dialogue}, \code{knowledge_query}, or \code{execution}. Dialogue and knowledge turns return a response to the dialogue owner without entering the planner. Execution turns additionally produce a candidate planner request; they do not contain an executable plan.

Candidate requests are published to the planner-admission endpoint. This endpoint is owned by \code{nao_orchestrator}, which normalises the payload, establishes goal lineage, and forwards only admissible requests on \code{/planner/request}. \code{planner_llm} generates a structured plan from that request and the AB registry. The resulting intent returns to the orchestrator, where deterministic checks validate plan metadata, skill names, arguments, and step ordering before any action or service is invoked. Step outcomes are published on \path{/planner/execution_feedback}; the planner supervisor may then complete the goal, request clarification, terminate safely, or issue a newer plan version.

This flow provides three runtime guarantees. A conversational response cannot accidentally become robot execution without crossing the admission boundary. A planner output cannot bypass registry and schema validation. Finally, planning-time context is evidence at time $T_0$, not proof of an execution-time effect: AB=1 skills must obtain fresh evidence where their result depends on the scene, robot state, or KnowledgeCore.

\section{ROS Nodes}

\subsection{\code{dialogue_manager}}

\code{dialogue_manager} retains ownership of the dialogue lifecycle and final user-facing speech. It receives ROS4HRI speech events, maintains the interaction context required by the chatbot service, and realises communication requests. This established component is reused rather than duplicated: planning and execution packages never call a speech backend merely because they have produced status information.

Planner dialogue acts return through the same ownership boundary. \code{planner_llm} publishes structured acknowledgement, clarification, failure, or completion acts on \path{/planner/dialogue_act}; \code{nao_orchestrator} relays the admitted act on \path{/nao_orchestrator/planner_dialogue_act}; and the dialogue layer chooses the final wording and speech mechanism. The relay keeps supervision observable while preserving one utterance author
ity per semantic event, which is essential for preventing duplicate acknowledgement and completion speech.

\subsection{\code{chatbot_llm}}

\code{chatbot_llm} is a lifecycle-managed semantic routing node built on the existing chatbot scaffold. Its turn callback receives a \code{DialogueInteraction}, preserves the supplied conversation history, queries the available knowledge snapshot, and combines it with the most recent \code{/scene/summary}. The \code{PlannerHandoff} adapter projects these sources into \code{grounded_context_v3}: a compact structure containing bounded entities, locations, relations, and a time-$T_0$ state summary rather than raw detector streams or an unresowledge graph.

The turn engine produces both user-facing text and a structured route. A \code{dialogue} route covers conversational turns and does not publish planner work. A \code{knowledge_query} route answers from current symbolic evidence without causing a physical action; consequently, a question such as ``what can you see?'' can use the current scene summary, whereas ``scan and tell me what you see'' is eligible for execution. An \code{execution} route constructs planner-facing metadata such as the goal text, request kind, normalised intent hints, and compact targets. It clears direct executable intents and publishes the candidate request to \code{/nao_orchestrator/planner_request}, ensuring that the chatbot cannot bypass admission or create skill sequences itself.

The canonical behavioural policy resides in \path{src/chatbot_llm/config/chat_prompt_pack.yaml}. Python builders provide structural framing and runtime context, while the prompt pack defines response and routing policy. The integrated profile uses \code{response_first} as the thesis baseline: a natural response is returned through the dialogue lifecycle while planner ingress remains separately observable. \code{intent_first} is retained as an ablation mode, not silently mixed into the scored baseline. Every turn also emits \path{/chatbot_llm/turn_trace}, recording the selected route, intent metadata, evidence visibility, and whether a planner handoff occurred.

\subsection{\code{planner_llm}}

\code{planner_llm} is the high-level planning and supervision node. It subscribes to admitted \code{/planner/request} messages rather than directly consuming chatbot output. Through \code{planner_common}, each request is normalised into the canonical contract with goal metadata nested under \code{plan}. The planner prompt combines the goal text, request kind, normalised intent hints, compact grounded context, canonical skill registry, permitted step types, and the required JSON output envelope. Planner policy is maintained in \path{src/planner_llm/config/planner_prompt_pack.yaml}; the runtime builder supplies request-specific structure without duplicating that policy in Python source.

The model response is not treated as executable merely because it resembles JSON. The planner engine extracts the candidate object, normalises its schema, validates required metadata and step fields, and applies a bounded repair retry when configured. Unsupported skill names, malformed arguments, invalid recovery policies, or unparseable output become typed failure or clarification outcomes. A deterministic shortcut exists only for a narrow, unambiguous primitive motion or posture request; it is not a general rule-based planner. Valid plans are published on \code{/intents} for independent orchestrator validation.

The node also subscribes to \code{/planner/execution_feedback}. Feedback is therefore part of the planning loop rather than a logging afterthought: it can advance supervision, expose a recoverable failure, request clarification, or trigger a revised plan. The planner never invokes a robot adapter and never speaks directly. Its user-facing output is a structured dialogue act that must cross the orchestrator relay and dialogue owner.

\subsection{Goal-Keyed Supervisor}

The planner supervisor keeps execution state under an active \code{goal_id}. Each accepted plan additionally carries a \code{plan_id} and monotonically meaningful \code{plan_version}; stable \code{step_id} values allow a newer version to preserve already completed work when a replan joins the same goal. Feedback from an older or unrelated version is rejected rather than being allowed to complete the current goal accidentally.

The supervisor distinguishes planning, replanning, waiting-for-user, completed, and failed states. Step feedback may move the goal forward, expose a recoverable condition, or produce a structured dialogue act. If a replacement plan is necessary, \code{planner_llm} creates and validates it under a newer version. \code{nao_orchestrator} never invents a local substitute plan, which preserves a single planning authority while keeping execution deterministic.

\subsection{Skill Registry (\code{skill_common})}

The planner-facing capability model is derived from the canonical \code{ab_registry.json} file in the \code{skill_common} defaults. A registry entry identifies a capability, its typed arguments, result shape, preconditions or evidence expectations, and admissible recovery behaviour. The planner selects from these entries instead of inventing NAOqi calls or undocumented action names. Runtime and documentation views are projections of this canonical file and are checked together for consistency.

The abstraction-boundary level expresses implementation maturity. AB=0 entries describe interfaces or lower-level primitives; AB=1 entries are executable runtime skills; and AB$\geq$2 entries remain proposals until they pass explicit promotion gates. The current AB=1 surface includes perception and reporting skills such as \code{scan}, \code{find_object}, \code{inspect_area}, and \code{report_result}. Navigation and manipulation are represented by \code{navigate_to}, \code{walk_to}, \code{bring_object}, \code{pick_object}, and \code{place_object}. Social, motion, and interaction capabilities include \code{perform_motion}, \code{look_at}, \code{wave_greet}, and \code{ask_user}; explicit symbolic operations are \code{kb_add}, \code{kb_revise}, and \code{kb_remove}. The same contract can be backed by a NAO adapter, simulator, or fake-skill server, allowing planner tests to preserve the execution API while changing the physical substrate.

\subsection{\code{nao_orchestrator} and the Execution Boundary}

\code{nao_orchestrator} is the deterministic boundary between model output and robot effects. At ingress, its planner gate admits candidate requests, normalises their contract, establishes lineage, and publishes \code{/planner/request}. At egress, it consumes executable intents, validates the nested plan against the registry and step schema, and rejects stale, duplicate, or unsupported work before dispatch. This two-sided role explains why the node appears at both admission and execution positions in Figure~\ref{fig:full-stack-architecture-plate}: it is one lifecycle component enforcing two distinct boundaries, not two planning nodes.

Accepted plans are dispatched in order through ROS actions or short request/response interfaces appropriate to each skill. The orchestrator tracks active plan and step state and publishes events including plan accepted, step started, step succeeded, step failed, and plan completed on \code{/planner/execution_feedback}. These events retain \code{goal_id}, \code{plan_id}, \code{plan_version}, and \code{step_id}, making a run reconstructable and allowing the supervisor to distinguish a failure from a stale callback. Explicit symbolic mutations are routed through \code{kb_skills}; ordinary questions and implicit LLM claims cannot write directly to KnowledgeCore.

On failure, the orchestrator reports the typed result and stops or waits according to the validated policy. It does not ask an LLM for an unregistered action, create a replacement plan, or fabricate success. Likewise, it relays planner dialogue acts but does not become a second conversational policy. These restrictions keep non-deterministic reasoning upstream of a small, auditable execution surface.

\section{Grounding and Knowledge}

\code{nao_scene_grounding} converts detector output into a provider-independent scene representation. It normalises labels and confidence fields, separates people from objects, stabilises local object identities, and publishes the current \code{/scene/summary}. Detector-derived facts may be mirrored as transient KnowledgeCore updates through \code{/kb/revise}, but the grounding node does not become a general world model. The detector profile can currently use the established perception backend, while its public summary prevents chatbot and planner packages from depending on provider-specific messages.

\code{kb_skills} is the transport boundary for \code{/kb/query} and \code{/kb/revise}. The chatbot obtains a bounded \code{knowledge_snapshot_v2} through this interface and combines it with \code{scene_summary_v2} to produce \code{grounded_context_v3}. This projection deliberately omits unrestricted raw evidence and keeps entities, locations, and relations within prompt-size bounds. Image-plane centres are retained as image evidence but are not interpreted as metric distance. Metric position or proximity requires a frame-qualified spatial overlay or fresh evidence from the responsible skill.

Planning context and execution evidence consequently have different roles. Current symbolic state is sufficient for a non-mutating knowledge answer and useful for selecting a plan. It is not sufficient to claim that an object was found after a scan, that a path remains clear, or that a manipulation succeeded. Skills that own those effects requery the relevant detector, robot, or KB seam at execution time and place the resulting evidence in their typed payload. This preserves truthful reporting when the world changes between planning and execution.

\section{Fake Skills and Simulation Seams}

The \code{fake_skills} package implements the same action-facing contracts as the AB=1 runtime surface while replacing hardware outcomes with controlled policies. Supported global modes include \code{scenario}, \code{always_success}, \code{always_fail}, \code{every_other}, and seeded pseudo-random execution. Named scenario and dynamic policy profiles can inject a failure at a particular stage, preserve scenario state across steps, and expose recoverability information. Results carry \code{metadata.fake=true}, and \code{/fake_skills/events} records dispatch and outcome evidence for later reconstruction.

This seam permits multi-step planner and orchestrator behaviour to be exercised without conflating software supervision with robot reliability. The all-success profile checks plan coverage and ordered dispatch; fail-once navigation or manipulation profiles check feedback, replan lineage, and non-repetition of completed steps; blocked-delivery and missing-recipient profiles check clarification or safe termination. KB guards and post-effects allow the scenario state to change in response to a successful fake action rather than being encoded only in prose.

The resulting evidence is intentionally qualified. A fake-skill pass supports claims about routing, plan validity, deterministic dispatch, feedback handling, and recovery policy. It does not demonstrate physical navigation accuracy, grasp success, detector quality, NAOqi timing, or human-robot safety. Chapter~\ref{chap:validation-methodology} therefore reports the fake-depth score separately from the main speech-ingress stack and identifies robot- or detector-dependent checks explicitly.

\section{Models and Runtime Configuration}

The integrated launch profiles in \code{nao_chatbot} select dialogue, chatbot, planner, grounding, orchestration, skill, and adapter components as a coherent runtime. Chatbot and planner backends are independently configurable through launch parameters and environment-backed provider settings; the current stack supports local or OpenAI-compatible model endpoints without embedding credentials or host-specific addresses in source. The exact model identifier, endpoint class, temperature, timeout, prompt-pack revision, and response mode are captured with each scored validation run because they affect latency and structured-output reliability.

The prompt packs and AB registry are runtime-critical configuration, not informal documentation. The chatbot prompt pack defines response and routing policy; the planner prompt pack defines planning policy and output requirements; and \code{ab_registry.json} defines the admissible capability surface. Changes to prompt wording are evaluated through the bounded SkillOpt process with a baseline, mutation batch, holdout checks, and an accept or reject decision. This prevents a favourable single example from silently changing behaviour at unrelated dialogue, KB, execution, report, or speech-ownership seams.

For reproducibility, final validation records whether \code{response_first} or the \code{intent_first} ablation was active, whether grounded-context digesting was enabled, which environment fixture was preloaded, which fake policy or real adapter profile was used, and whether object detection was launched. Local inference removes external quota dependence but still requires model and hardware metadata; hosted inference requires the same metadata plus endpoint and quota conditions. These run-level facts are part of the evidence bundle defined in Chapter~\ref{chap:validation-methodology}, rather than being assumed from a developer's shell configuration.
