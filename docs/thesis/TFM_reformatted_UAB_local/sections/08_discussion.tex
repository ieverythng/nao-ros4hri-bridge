\chapter{Discussion}
\label{chap:discussion}

\section{What the Final Evidence Demonstrates}

The strongest result is not that the language model behaved identically across prompts or backends. It did not. The strongest result is that the architecture separated model-generated proposals from deterministic admission and execution sufficiently to observe, reject, or contain the recorded variation.

The primary frozen evaluation produced 64 passes and eight failures across 72 records. The controlled environment and stateful KB profiles passed 11/11 and 7/7 respectively, while the repeated robustness profile passed 12/15 and the capability-extreme profile passed 5/7. The beginning-stage navigation failure and middle-stage pick failure both produced feedback-driven replans with new plan versions; the navigation case also retained complete target coverage and terminal closure. These results support the use of explicit contracts, reviewed skills, typed feedback, and versioned orchestration for bounded language-guided execution.

The failures also define the boundary of that claim. Universal target sets were occasionally incomplete, one multi-turn case omitted closure, one missing-recipient probe did not express the required clarification, and two capability-extreme plans omitted required actions. The architecture prevented the two incomplete plans from executing and did not invent success for unselected members. It did not, however, repair every semantic omission or guarantee a user-facing closure in every recovery case.

\section{Model-Independent Interfaces and Model-Dependent Behaviour}

The runtime interfaces were stable across the primary Qwen3-VL configuration, the Qwen3.5 and cloud-model screening runs, the Gemma fallback smoke test, and the deterministic simulated-skill profiles. Planner requests, compact grounded context, plan admission, execution feedback, and dialogue acts retained the same architectural roles. This is the sense in which the design is model-agnostic: a model can be changed without redefining the owned interfaces.

Behavior was not model-invariant. Qwen3-VL supplied the only complete frozen qualification; Qwen3.5 and the Ollama models had narrower and mostly failing capability-extreme evidence. The current \code{gemma4:31b-cloud} fallback passed readiness checks and one dialogue smoke turn only. It cannot inherit the Qwen3-VL qualification merely because it uses the same endpoints and schemas.

This distinction is central to the thesis. Model-agnostic integration means stable contracts and a repeatable qualification procedure, not equal output quality from every compatible model. A new model must pass the same questionnaire, robustness repetitions, failure injections, and capability-extreme cases before it can replace the qualified primary.

\section{Questionnaire-Level Interpretation}

The end-to-end questionnaire contains 22 exercised requirements and produced 20 passes and two failures. This result combines simple dialogue, KB checks, single-skill execution, composite execution, and route safety under one integrated evaluation path.

The first failure is a route error. The red-cup update changed KnowledgeCore successfully, but it entered the execution planner and used \code{kb_add}. Under the final architecture, KB maintenance belongs to the knowledge component and must not be presented as a planner-visible robot skill. The second failure is a semantic role error. The kitchen delivery case selected the kitchen as a recipient, clarified, and stopped without execution. The stop was safe, but the plan path did not preserve the kitchen as a location and the operator as the recipient.

The recorded \code{wave_greet} case requires a similar boundary. The behavior of navigating, waving, and reporting passed, but the canonical skill taxonomy represents a wave as a named \code{perform_motion}. The trace supports the behavior, not an independent test of that twelve-skill projection.

\section{Grounding, Roles, and Symbolic State}

Compact symbolic grounding was sufficient for the controlled environment and stateful KB chains. Objects, people, locations, support relations, colours, and post-action state remained queryable across the positive profiles. This confirms the value of providing the planner with a bounded symbolic projection rather than asking it to reconstruct state from dialogue history alone.

The failures show why grounded context must not be confused with grounded selection. The correct entities can be present while the model omits one member from an \enquote{all objects} request or assigns a location to the recipient role. The critical interface boundary is therefore the transition from available evidence to authoritative target selection. Validation must compare requested, selected, planned, executed, and reported members and must preserve role constraints at each boundary.

Knowledge postconditions also matter independently of a successful skill response. A report should be treated as true only when the execution evidence and required state change agree. The 7/7 stateful chain supports this mechanism under the controlled fixtures, while the missing closure case shows that correct intermediate behavior still requires one explicit terminal outcome.

\section{Planning, Admission, and Replanning}

The capability-extreme results distinguish planning quality from execution safety. Five long composites were represented adequately, while two model-authored plans omitted required actions. Both incomplete plans were rejected before dispatch. This is preferable to executing a reduced plan and reporting the original request as complete, but it remains a task-level failure.

The fail-once navigation case provides the clearest beginning-stage recovery evidence. Failure was injected on the first navigation call, correlated feedback was returned, the plan version advanced, the four-target objective was preserved, and the revised execution closed. A separate pick trace exercised the middle of a goal: object finding succeeded, the second-step pick failed, and the revised plan executed scan, find, pick, and report. The architecture can therefore support both complete and remaining-work replanning when failure evidence, objective lineage, and available recovery skills are explicit.

Recovery is less mature for later and terminal failures. A blocked-delivery trace reached the manipulation stage and produced replanning, but did not close; the missing-object case truthfully searched and asked for help but also lacked closure; and the targeted missing-recipient case did not express the expected clarification. The deterministic boundary constrained execution, yet dialogue and closure still depended on model-generated content. Safe non-execution and successful task recovery should therefore remain separate metrics.

\section{Application Ablations and Non-Determinism}

The application ablations did not identify a sampling or token setting that removed semantic variance. Published sampling was slower without a semantic gain, deterministic sampling did not improve the smoke result, and larger token budgets did not repair the capability-coverage failure. Adjusted timeouts improved operational tolerance but did not change the semantic limits.

The A0 discrepancy between automated trajectory checks and manual semantic assessment reinforces the need for layered evidence. All six expected trajectories were present, whereas manual review accepted five of the six responses. Event checks can confirm route and execution presence while semantic review can still identify incomplete wording. Both observations are therefore retained.

Repeated tests are consequently necessary even when the runtime tuple is frozen. The robustness sequence of 5/5, 4/5, and 3/5 shows that a single passing sample would overstate reliability. The stable architectural claim is that failures remained observable and bounded, not that the same model always generated the same valid plan.

\section{Controlled Skill Adapters, Physical Claims, and Portability}

Deterministic simulated adapters were valuable because they exposed success, failure, replanning, world-state updates, and reporting under controlled policies while retaining the robot-facing result contract. Their evidence supports software-level claims about admission, dispatch, recovery, and symbolic effects. It does not establish physical navigation accuracy, grasp reliability, manipulation success, or human-robot safety.

The stack is partly platform-independent and partly NAO-specific. The planner request, planner output, execution feedback, dialogue act, and compact grounding contracts can be reused if another platform supplies an equivalent reviewed skill registry and typed adapters. Speech execution, replay motion, posture control, head motion, and look-at behavior in this implementation depend on NAO packages or adapters. Cross-platform reuse is therefore an architectural proposition, not a demonstrated physical result.

ROS~2 and ROS4HRI provide useful modular boundaries but also introduce lifecycle, remapping, dialogue-state, transform, and availability dependencies \parencite{quigley2009ros,macenski2022ros2,mohamed2020ros4hri}. Preflight and trace correlation are part of the experiment because a component that is present but inactive can otherwise resemble a model failure.

\section{Implications for the Research Questions}

RQ1 is supported for the tested task families, with explicit failures on one questionnaire composite and two capability-extreme cases. RQ2 is supported strongly in controlled symbolic profiles, but target selection and role assignment remain model-sensitive. RQ3 is supported by rejection of incomplete plans and by the absence of unregistered dispatch in the retained evidence. RQ4 is supported directly for fail-once navigation and only partially for missing-object and missing-recipient recovery. RQ5 is supported at the interface and auditability level, while equivalent behavior on another robot or model remains unqualified.

The overall interpretation is consequently measured: the architecture converts many language-model failures from silent execution risks into explicit route, selection, plan, clarification, or closure failures. That is a meaningful safety improvement, but it is not a proof of unrestricted autonomy or exhaustive safety.
