\chapter{Discussion}
\label{chap:discussion}

\section{Architectural Findings}

The implementation and runtime traces show that modular planning can be inspected at boundaries that are absent from a prompt-to-action design. The planner does not own robot execution, speech output, or raw perception. It receives structured requests and returns structured plans or dialogue acts. Direct atomic execution was retained as an orchestrator control path, but it was not treated as a matched experimental baseline because its capability scope differs from multi-step planner mediation.

The boundary between \code{planner_llm} and \code{nao_orchestrator} is especially important. The planner proposes work over the reviewed skill registry, while the orchestrator independently validates and dispatches it. This permits the same planning path to be exercised with real adapters, deterministic fake skills, or unavailable skills without changing planner ownership. Execution feedback can then return as a typed planning input rather than an unstructured backend error. The architecture therefore constrains where model output may influence the robot, although the semantic audit shows that separation alone does not guarantee correct target selection or post-action state.

This result is consistent with research that questions the reliability of unconstrained language-model planning and instead grounds model proposals in available actions or callable APIs \parencite{huang2022zeroshot,ahn2022saycan,liang2022codepolicies,valmeekam2023planning}. The implemented contribution is a modular NAO integration in which request admission, skill availability, execution, feedback, and user-facing closure remain attributable to named owners and interfaces.

\section{Harness Engineering and Failure Attribution}

The development and validation evidence shows that harness engineering is necessary when evaluating a language model connected to a live robot environment. Several failures initially appeared to be dialogue or planning problems but originated elsewhere. A complete KB fixture could be projected without producing an authoritative target selection; a successful action result could leave mutually inconsistent location facts; and a complete ROS trajectory could preserve the wrong object or person roles. Prompt inspection alone cannot distinguish these cases.

The runtime harness establishes the evidence chain needed for that distinction. It verifies source and image identity, lifecycle and QoS readiness, fixture insertion, KB state, dialogue isolation, and action-server availability before injection. During a case, it relates the emitted utterance to route selection, admitted planner context, selected entities, the candidate plan, dispatched skills, execution feedback, KB postconditions, structured reporting, and speech. It also preserves failures and isolated reruns rather than replacing them with a later successful probe. Together, these checks determine which claims a run can support.

The implemented harness remains tailored to this stack. A reusable environment-adaptive harness would require explicit adapters for readiness, fixture and state control, interaction ingress, semantic oracles, failure injection, and evidence export. The development history suggests that such a harness would reduce diagnostic ambiguity and limit the tendency to treat integration faults as prompt faults. The thesis does not quantify the engineering effort that would have been avoided, so this remains a design implication rather than a measured productivity claim.

\section{Prompt Packs and Skill Contracts as Runtime Policy}

The chatbot and planner prompt packs behaved as versioned runtime policy rather than informal prose. They defined the model's role, route labels, planning constraints, and output expectations, while the Python builders supplied stage-specific structure and the current request context. Treating these packs as configuration made their revision, hashing, and bounded comparison part of the run tuple. It also prevented a local wording workaround from becoming an unrecorded change to dialogue, grounding, planning, or reporting behaviour.

The evidence further shows why prompt changes should follow failure attribution. A prompt mutation cannot restore a fact that never entered the KB, repair an expired fixture, provide a missing canonical identifier, or remove a stale postcondition. Conversely, a complete grounded context does not ensure that the model will use the correct entities or return valid planner JSON. The bounded prompt-revision procedure therefore evaluates route safety, KB use, execution admission, reporting, and duplicate-speech holdouts before accepting a policy change. This is a narrower claim than general prompt optimisation: it is regression control for two runtime-critical prompt packs.

The reviewed skill registry provides the complementary capability policy. ROS action and service definitions specify transport-level fields, but they do not by themselves explain to a language model when a skill is applicable, what evidence constitutes success, which effects are expected, or which failures may require clarification or replanning. Contract~4 adds planner-facing parameters, grounding requirements, declared preconditions, expected effects, observable success evidence, known failures, recovery guidance, availability, and executor mapping. The same entry informs prompt construction, deterministic admission, dispatch, and result interpretation.

This design resembles the broader principle behind affordance-constrained planning and API-grounded policy generation \parencite{ahn2022saycan,liang2022codepolicies}. In this stack, however, the registry remains a reviewed declaration rather than a learned affordance model or a formal proof system. It narrows the proposal surface and makes unsupported work rejectable, but it cannot guarantee that a semantically valid combination of registered skills has been selected. The F11 invalid-output pressure and the F13 target-role failures demonstrate these distinct limits.

\section{Planner Behaviour and Feedback}

The planner design is strongest when the task can be represented as a sequence of available skill contracts. Atomic commands, object search, navigation, and report-generation tasks map naturally to the registry. Composite instructions are harder because they require the planner to preserve partial order, carry evidence between steps, and decide whether later work remains valid after an earlier failure. These findings support RQ1 for the frozen task families rather than for unrestricted natural-language planning.

The deterministic failure profiles showed that recovery quality depends on both feedback lineage and the availability of a semantically different valid plan. Navigation fail-once cases produced newer plan versions and truthful closure in the strongest historical sweep. Pick and blocked-delivery cases were less stable, and some traces reached a safe stop without complete post-terminal closure. Feedback therefore enabled bounded replanning and clarification, as proposed by interaction-oriented planning approaches \parencite{huang2022innermonologue,yao2022react}, but the evidence does not support a general recovery guarantee for RQ4.

The deterministic guards contain malformed model output and do not form an alternative planner. Route checks, schema validation, registry lookup, argument checks, lineage comparison, and deduplication reject or normalise a bounded set of invalid outputs. Planner compatibility repairs run only after the model path and validation retry, remain visible in the trace, and return typed failure when their conditions do not hold. This order preserves the LLM as the source of planning decisions while preventing malformed output from becoming direct robot work.

\section{Grounding, Identity, and World State}

Grounding remains a central limitation. The architecture distinguishes \code{grounded_context}, the detector-derived scene summary, and raw KB evidence because each has a different role. The chatbot needs a bounded symbolic projection, the planner needs actionable identifiers and roles, and operators need source evidence with freshness and provenance. The F13 semantic audit showed that presence in the projection is insufficient when target roles are not preserved through selection, planning, dispatch, and reporting.

The gold-apple handoff provides a narrower example. The fixture exposed the apple and named recipient, but the authoritative selected set was empty and admission ended in clarification. This was a truthful stop because no unsupported placement was executed, yet it was not a successful use of complete context. The case separates context availability from target resolution and shows why RQ2 must be evaluated across the whole handoff rather than by searching a prompt trace for an entity name.

Person handling exposes a related semantic requirement. Tracked-person state and KnowledgeCore facts may identify a named individual, but downstream projections must retain whether that entity is a recipient, a gaze target, or another human participant. A person must not be promoted to a movable object or location because a malformed relation places it near an object. The same requirement applies to tables, rooms, and other supports that can anchor an instruction without becoming members of the requested object set. Typed KB classes, explicit task roles, and case-level forbidden-target checks therefore complement the compact projection.

Stable KB insertion probes separated fact availability from model use. Name, colour, support, and count queries passed in broad runs, while grouped post-effect queries exposed stale location relations after apparent delivery success. This confirms the value of symbolic state for bounded grounding, as also motivated by robot knowledge frameworks \parencite{tenorth2013knowrob,tenorth2017knowrob,saxena2014robobrain}. It also shows that planning-time state and verified execution-time state must remain separate. A fact used to choose a plan cannot establish that the plan later changed the world as intended.

\section{Execution Evidence and Truthful Closure}

Contract~6 makes the skill result the owner of fresh execution evidence. For state-changing skills, the result may also declare KB effects that the orchestrator applies through \code{kb_skills} and verifies through a later query. This creates two related but distinct checks: whether the action server returned a typed success and whether the expected symbolic postcondition became observable. The stale-location findings show why both are required.

Reporting adds a further evidence transformation. The planner may request \code{report_result}, but it cannot predeclare the result text of a sensing, navigation, motion, or manipulation step. The orchestrator accumulates typed results, and the reporting path derives its structured outcome from successful and failed execution evidence. A valid terminal report must cover the selected members, preserve recipients and anchors as roles rather than completed objects, and avoid claiming effects whose postconditions were not verified. Exactly-once speech is necessary at this boundary, but a single utterance can still be semantically incomplete.

Deterministic fake skills were valuable because they exposed success, failure, replanning, KB effects, and reporting under controlled policies. Their results support software-level claims about admission, lineage, dispatch, recovery, and symbolic state. They do not establish physical navigation accuracy, grasp reliability, or human-robot safety. This distinction keeps the fake-skill evidence useful without treating simulation semantics as embodied performance.

\section{ROS 2 and HRI Modularity}

The stack is partly robot-agnostic and partly NAO-specific. The planner request, planner output, execution feedback, dialogue act, and compact grounding contracts are not inherently tied to NAO. Reuse on another ROS-compatible platform would require an equivalent reviewed skill registry and adapters that produce the same typed evidence. Speech execution, replay motion, posture control, head motion, and look-at behaviour remain dependent on NAO-specific packages or adapters, so cross-platform portability was not demonstrated.

ROS~2 distribution and reusable HRI interfaces introduce integration costs as well as useful boundaries \parencite{quigley2009ros,macenski2022ros2,mohamed2020ros4hri}. Lifecycle state, QoS, topic remapping, per-person dialogue state, action availability, and transform ownership can each invalidate a run without appearing as a planner exception. The preflight and evidence-bundle requirements in Chapter~\ref{chap:validation-methodology} are therefore part of preserving the public interaction contract rather than incidental deployment checks.

The ownership split also prevents convenient shortcuts from becoming architectural drift. \code{dialogue_manager} retains dialogue lifecycle and final speech realization; \code{chatbot_llm} owns user-facing language, route selection, and candidate planner ingress; \code{planner_llm} owns plan generation and feedback-driven planning responses; \code{nao_orchestrator} owns admission, deterministic dispatch, feedback, and planner-dialogue relay; \code{kb_skills} owns KnowledgeCore transport; and runtime skills own fresh evidence for their effects. This separation makes failures more numerous as observable categories, but fewer of them can cross silently from model output to robot action.

\section{Validation Implications}

The difference between the F13 trajectory result and semantic audit is the principal methodological finding. A case can contain speech ingress, planner admission, execution feedback, a terminal marker, and final speech while still acting on the wrong targets. Full user-turn injection remains necessary for route correctness, dialogue ownership, and exactly-once speech. Planner and action-level probes remain useful for isolating plan admission and skill guards. Neither is sufficient without an oracle that compares requested, selected, planned, executed, and reported members and then verifies the resulting KB state.

The runtime-review index is useful for operational triage, but it remains secondary to explicit denominators and acceptance rules. The earlier trajectory assessment and later semantic cap describe different evidence depths rather than a uniform performance decline. Reporting both exposes the stronger acceptance criterion instead of suppressing a safety-relevant finding to preserve a headline score. The numerical rates determine how often the declared contracts held in the frozen cases; they do not estimate unrestricted task success or physical robot performance.

The research questions therefore receive different kinds of support. RQ1 concerns plan coherence over the frozen skill families. RQ2 requires entity and role consistency from source evidence through post-state verification. RQ3 concerns rejection of schema-invalid, registry-invalid, argument-invalid, and lineage-invalid work, not the elimination of all model errors. RQ4 depends on injected failures and traceable plan-version transitions. RQ5 is supported most directly by the named ownership boundaries and the harness evidence needed to inspect them. This division keeps the interpretation aligned with scenario-based validation rather than a broader claim of general robotic autonomy.
