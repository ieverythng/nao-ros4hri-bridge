End-to-End User -> Planner Dialogue Flow

Supervisor walkthrough pack for conceptual architecture + concrete JSON seams. This document is tuned for tomorrow's live presentation and mirrors the current branch contracts.

Date: 2026-06-01 Stack: chatbot_llm + planner_llm + nao_orchestrator Policy: Hybrid Minimal T0 Dialogue: direct planner act flow

Objective

Explain the full runtime path from user utterance to execution and dialogue act emission, with field-level contract clarity.

Ownership Principle

Planner consumes compact T0 evidence for reasoning. AB=1 skills resolve live world state at execution time from AB=0 sources.

Why this matters

Improves seam clarity, reduces payload duplication, and keeps ROS4HRI ownership boundaries deterministic.

1) Conceptual E2E Sequence

1
User -> chatbot_llm
Natural-language command enters route and intent parsing.
2
chatbot_llm -> orchestrator
/nao_orchestrator/planner_request with planner request JSON in Intent.data.
3
orchestrator -> planner_llm
/planner/request after gate/admission policy.
4
planner_llm -> orchestrator
/intents with canonical plan object.
5
orchestrator -> AB=1 skill
Skill execution dispatched via registry + AB policy.
6
AB=1 skill -> AB=0 sources
Live evidence resolution via scene/KB/tracked-person seams.
7
orchestrator -> planner_llm
/planner/execution_feedback with typed result payload.
8
planner_llm -> dialogue_manager
/planner/dialogue_act direct-mode act; relayed to user.

Dialogue mode policy is direct planner dialogue-act flow only (legacy fallback branches removed).

7) Replan Lineage and Join Behavior

  1. Single active-goal queue model.
  2. goal_id tracks goal continuity.
  3. plan_id + plan_version track plan lineage.
  4. Mid-join strategy: continue from mapped active step_id when possible.
  5. Fallback strategy: front-join from first pending step when mapping fails.
  6. Duplicate suppression uses exact tuple: goal_id, plan_id, plan_version.
