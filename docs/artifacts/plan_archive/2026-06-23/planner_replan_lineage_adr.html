ADR: Planner Replan Lineage And Hybrid T0 Contract

Accepted on 2026-05-31 for feat/TFM-LLM_planner.

Status: Accepted

Context

  • Planner payload seams had redundant metadata at multiple levels.
  • goal_token and world-model text/snapshot fields were stale.
  • Acknowledgement wording ownership was mixed between planner and chatbot seams.
  • Executor required deterministic continuation when receiving newer plans for the same goal.

Decision 1: Canonical planner payload shape

  • Planning metadata is canonical under nested plan.
  • Removed fields: goal_token, world_model_snapshot, world_model_text, planner-level ack_mode, planner-level raw ack_text.

Decision 2: Hybrid Minimal T0

  • Keep grounded_context.knowledge_snapshot, scene_summary, and state_t0.
  • knowledge_snapshot: compact KB references (normalized_name, id, type).
  • state_t0: deterministic planning facts (observer, backend, captured_at_sec, source/recency fields).

Decision 3: Orchestrator lineage + replan join

Single active goal queue model
goal_id = goal continuity
plan_id + plan_version = plan lineage
Mid-join by step_id, else front-join fallback

Duplicate suppression checks exact active tuple: goal_id, plan_id, plan_version.

Decision 4: Transition contract without token locks

  • new_goal: accepted when no active goal or by supersede policy.
  • goal_update: must match active lineage.
  • clarification_answer: must match active lineage.
  • cancel_request: clears active lineage.

Decision 5: Dialogue ownership guardrail

  • Planner emits dialogue acts and intent-level reasoning.
  • User-facing completion wording remains chatbot-owned via planner-dialogue relay path.
