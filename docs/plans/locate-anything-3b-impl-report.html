Executive Summary

LOCATE-ANYTHING-3B is a 3B-parameter visual grounding model: it takes image + text query and returns bounding boxes for matching objects. For the NAO / ROS2 / HRI bridge, the cleanest integration path is to treat it as a query-driven perception backend, not as planner logic.

Recommended deployment: start with remote inference on Juan's RTX 5070 Ti using locate-anything.cpp in CLI/shared-library mode, then expose a ROS2 service to the robot. Keep NAO-side execution thin: camera capture, request packaging, result publishing, and HRI feedback. Local-on-NAO deployment is useful only as a constrained fallback or proof-of-concept.

2. Architecture Overview

The integration should preserve the current NAO / ROS2 / HRI separation of concerns:

  • Perception handles image capture and model inference.
  • Bridge/orchestration converts raw detections into contracts the rest of the system can consume.
  • HRI turns results into robot behavior: speech, gaze, and clarification loops.

Recommended runtime flow

User request / planner intent
  → capture current image frame
  → create grounding request {query_text, image, camera_info, request_id}
  → LOCATE-ANYTHING-3B inference
  → parse bounding boxes
  → publish /perception/ground_text result and /scene/grounding_result
  → optionally update /scene/summary and world-model snapshot
  → HRI response: “I found the mug on your left” + look_at / gesture

3. Deployment Options: Local vs Remote

Two deployment modes are viable. They should share the same ROS2-facing contract so the rest of the bridge does not care where inference runs.

Option A — Local inference on NAO / robot-side host

DimensionAssessment
ProsNo network dependency, simpler privacy boundary, single-box operation.
ConsNAO-class hardware is resource-constrained for a 3B VLM; CPU-only latency will be high and interactive HRI will degrade.
Best useFallback mode, lab proof-of-concept, low-rate scans, offline testing.
Implementation modePrefer CLI wrapper first; if sustained local use is required, move to shared library to eliminate process overhead.
RiskThermal, memory, and latency pressure; possible ROS callback starvation if not isolated.

Option B — Remote inference server on Juan's RTX 5070 Ti

DimensionAssessment
ProsStrongest performance envelope, likely sub-second q8_0 inference, clean separation between robot control and GPU workload.
ConsNetwork dependency, serialization overhead, operational complexity, need for health checks and retries.
Best usePrimary production path for interactive object-finding and HRI.
Implementation modePersistent inference daemon or service wrapping liblocate_anything / C ABI.
RiskDropped connectivity, stale frames, robot waits on remote result if timeouts are not well bounded.

Recommended decision

Primary: remote GPU inference on the RTX 5070 Ti.

Fallback: local CLI mode for degraded operation and diagnostics.

Why: HRI interaction quality depends on predictable latency. The robot should spend its compute budget on control, speech, and bridge logic rather than large-model inference.

Deployment contract to keep stable

ROS2 request
  request_id: string
  query_text: string
  image: sensor_msgs/Image or encoded buffer
  camera_info: sensor_msgs/CameraInfo
  decode_mode: hybrid|slow|fast

ROS2 response / topic payload
  success: bool
  backend: locateanything-3b
  model_name: LocateAnything-3B-q8_0
  image_frame: string
  timestamp: builtin_interfaces/Time
  detections: [{label, score, bbox, center_px, attributes?, pose_hint?}]

Detailed phased plan

Phase 1 — Minimal viable bridge

  • Create a Python ROS2 node that subscribes to camera frames and exposes a grounding service.
  • Invoke locate-anything-cli detect --model ... --input ... --prompt ....
  • Parse JSON detections and publish result payloads.
  • Keep current continuous detector path untouched to reduce blast radius.

Phase 2 — Planner/HRI integration

  • Add query-specific topic /scene/grounding_result.
  • Teach the orchestration layer to call grounding on demand for find_object-style intents.
  • Add HRI responses based on 0, 1, or many matches.

Phase 3 — Production backend

  • Replace subprocess spawn with persistent backend using liblocate_anything or la_capi.h.
  • Support local and remote runtime behind the same adapter interface.
  • Add metrics, health checks, watchdog restart, and circuit-breaker behavior.

Phase 4 — Actionable grounding

  • Add camera calibration and optional depth/TF support.
  • Emit pose_hint when geometry is available.
  • Allow planner to chain grounded perception into look_at or navigation safely.

6. Key Code Patterns

The local codebase inspection strongly suggests a staged adapter pattern: start simple, keep interfaces stable, then swap runtime implementations without touching planner/HRI contracts.

Pattern A — Backend interface with multiple implementations

from dataclasses import dataclass
from typing import Protocol

@dataclass(slots=True)
class GroundingRequest:
    request_id: str
    query_text: str
    image_path: str | None
    image_bytes: bytes | None
    decode_mode: str = "hybrid"

@dataclass(slots=True)
class Detection:
    label: str
    score: float
    bbox: tuple[float, float, float, float]

@dataclass(slots=True)
class GroundingResult:
    success: bool
    backend: str
    model_name: str
    detections: list[Detection]
    message: str = ""

class GroundingBackend(Protocol):
    def locate(self, request: GroundingRequest) -> GroundingResult: ...

Why: this keeps node.py independent from whether inference happens via CLI, C API, or remote server.

Pattern D — ROS2 node shape

class LocateAnythingNode(Node):
    def __init__(self) -> None:
        super().__init__("locate_anything")
        self._frame_buffer = FrameBuffer(max_age_sec=1.0)
        self._backend = build_backend(self)
        self._result_pub = self.create_publisher(String, "/scene/grounding_result", 10)
        self._service = self.create_service(GroundText, "/perception/ground_text", self._handle_ground_text)
        self._image_sub = self.create_subscription(Image, "/camera/image", self._on_image, 10)

    def _handle_ground_text(self, request, response):
        result = self._backend.locate(to_grounding_request(request, self._frame_buffer.latest()))
        publish_grounding_result(self._result_pub, result)
        return fill_response(response, result)

This matches the explicit composition style seen in iTrack's application factory/config organization: thin entrypoints, settings object, delegated services.

7. Testing Strategy

Testing should cover both the model backend seam and the robot-behavior seam. The inspected locate-anything.cpp repo already includes strong backend verification signals: ctest-backed frozen references and scripts/diff_upstream.py for live parity against the official implementation. Reuse that confidence rather than re-solving model correctness from scratch.

LayerWhat to testMethod

Normalizationbbox conversion, score handling, center calculation, schema stabilityPure Python unit tests

Topic publishingGrounding result topic shape and timingLaunch tests + subscriber assertions

Deployment pathRemote reconnects, health checks, local fallbackFailure-injection tests and network interruption drills

Recommended test ladder

  1. Golden backend tests: use saved CLI outputs and fixed images.
  2. ROS2 contract tests: send a grounding request and assert normalized result contents.
  3. Scenario tests: "find the mug", "find the person", "no object found", "two mugs present".
  4. Operational tests: kill remote backend, verify timeout + apology + retry/fallback.
  5. Human-loop tests: confirm robot phrasing and gesture timing feel natural.

Ambiguous groundingMediumOpen-vocabulary prompts can match multiple items.Add HRI clarification policy and richer disambiguation metadata.
Camera/frame stalenessMediumRobot may act on an old frame if request timing is loose.Use request IDs, frame timestamps, and max-age checks.

Schema fragmentationMediumDifferent consumers may expect center-only or bbox-rich results.Version the payload and preserve a normalized canonical schema.

Top implementation guidance

Do first

  • Define one stable grounding service contract.
  • Implement CLI adapter quickly.
  • Use remote GPU as the default path.
  • Add explicit timeout and error messaging.

Do next

  • Promote backend to persistent shared-lib service.
  • Publish richer scene evidence for planner use.
  • Add HRI disambiguation patterns.

Do not do early

  • Do not embed heavy inference inside the planner loop.
  • Do not assume 2D bbox == navigation target.
  • Do not make local-NAO inference the only production mode.
