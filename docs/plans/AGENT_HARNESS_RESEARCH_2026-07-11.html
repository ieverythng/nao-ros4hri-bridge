Agent Harness Research Plan

Watson/Hermes-style applied harness, 2026-07-11

Position

The harness should start as a typed environment layer around the seams already validated in the NAO ROS4HRI stack: dialogue, planner request, execution feedback, KnowledgeCore mutation, artifacts, and runtime traces. Once stable, the same shape can support non-robot applied-agent work.

Core Architecture

User / evaluator
  -> Harness session controller
  -> Role router
     -> response model
     -> intent model
     -> planner model
     -> critic model
  -> Environment adapter layer
     -> ROS4HRI adapter
     -> workspace/code adapter
     -> browser/service adapter
     -> future trading/simulation adapter
  -> Tool schema registry
  -> Postcondition checker
  -> Trace and replay store
  -> HTML/operator dashboard

Design Principles

Typed stateEnvironment state must be bounded, inspectable, and replayable.
Model rolesResponse, intent, planning, critique, and summarization are separate jobs.
PostconditionsClaims are unproven until checked against KB, execution feedback, or artifacts.
ROS ownershipThe harness observes and requests through accepted seams; it does not bypass orchestrator or KB skills.

Ablation Lessons

  • Qwen/Watson improves natural wording, but fluency alone did not fix fake-deep or KB postconditions.
  • Runtime parameter mutation is not a reliable model-ablation boundary. Launch role bindings must be explicit.
  • Planner JSON validity is not enough. Mixed mode still failed KB revise/remove and fake-deep handoff.
  • Grouped delivery needs stale-location and human/object leakage checks.
  • Speech instrumentation failures should be separated from planner and executor failures.

Grilling Checkpoints

Start pointRecommended: evolve the runtime-review scripts into a harness.
GeneralizationRecommended: keep ROS4HRI as one adapter under a general core.
RolesRecommended: configure response, intent, planner, critic, and summarizer independently.
EvidenceRecommended: make postconditions mandatory for research-grade runs.

Milestones

  1. Ablation ledger with role bindings, launch args, endpoint checks, artifacts, and scores.
  2. Replayable runtime session manifest around questionnaires and architecture sweeps.
  3. Role router for independently configured models.
  4. Postcondition DSL for KB, execution, report-result, and human/object assertions.
  5. Watson ROS adapter.
  6. Applied-agent adapters for workspace, service/browser, and iTrader-style simulations.

Risks

Main risks: overfitting to the thesis stack, treating prompt text as the only control surface, direct KB writes outside fixtures, scoring launch failures as model failures, and accepting natural language reports without world-state evidence.
