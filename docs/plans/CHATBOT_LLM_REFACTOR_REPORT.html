chatbot_llm Refactor Report — Tighten & Re-own

30 June 2026. Two-phase deslop of the chatbot_llm turn engine: a behaviour-preserving structural split (Phase 1) plus a diagnose-first, SkillOpt-gated reduction of deterministic over-reach (Phase 2).

Primary objectiveMake the self-authored turn logic small, honestly-owned, and reactive — the LLM leads each turn and deterministic fallbacks only nudge instead of silently overriding the model.
Phase 1Done — behaviour-preserving. 2772-line turn_engine.py split into four focused modules; dead code removed; 137 focused tests pass as an equivalence oracle.
Phase 2Live-validated. Open-domain wording mutation rejected (live answers already warm); only the duplicated-label deslop applied under a passed unit + live gate; safety guards kept (overrides are beneficial nudges, 16.7% rate).
Score postureDemo baseline response_first 8.2 qualified / 8.7 success-path held; live smoke + intent_ablation pass all scored seams with exactly-once speech.

This pass avoids deterministic shortcuts that hide runtime limits. It separates the "nudge" vocabulary from orchestration, keeps anti-fabrication and anti-duplicate-speech wording in one place, and exposes a per-turn ROUTE_DECISION trace so the override rate between the model's own route and the resolved route can finally be measured.

Why this was safe to do here (ownership map)

chatbot_llm is a nested repo with an upstream (IIIA SocialMinds) remote, so "narrow, compatibility-conscious changes" is the default. The files in scope are purely self-authored (no upstream lineage), which licenses a full deslop.

The problem: a deterministic override cascade fighting the model

turn_engine.py had grown to 2772 lines holding, in one module: ~20 text classifiers, a ~210-line _resolve_planner_mode_turn override cascade that re-decided the route after the LLM, the intent-first _lock_intent_first_route mirror, and ~12 acknowledgement/report fallback builders. Deterministic guards could re-classify turns the model may already have routed correctly, so turns could fail or converge onto canned fallbacks rather than the LLM's own answer. Fallbacks that replace the model instead of nudging it are reward-hacking: they make the harness look healthy while masking what the LLM would do.

Prompt / LLM contract discipline

Exactly one LLM-facing change was made, and it went through the gate first (the SkillOpt ledger entry pre-existed the edit, honouring the root AGENTS.md rule "do not patch prompt text first and create the ledger afterwards"). Only after a live baseline existed was the duplicated grounded-context label collapsed to a single Grounded context for this turn: header, with the three locking test_turn_engine.py assertions updated in the same change. The over-restrictive open-domain wording mutation was rejected because the live holdout proved the current wording is already warm. Decisions and evidence: docs/artifacts/chatbot_llm_phase2_skillopt_2026-06-30.md (Live holdout result).

Seams that could still be improved

  1. Push KB-vs-dialogue disambiguation into the prompt, shrink the guard. The single recurring override is knowledge_query→dialogue (16.7% of turns) on reflective/preference/future questions. The healthy fix is to teach the prompt pack when a question is conversational vs a live world-state query so the model stops over-emitting knowledge_query and the guard becomes a rare safety net. Gate with the same live intent_ablation holdout.
  2. Sharpen the Phase-0 trace. ROUTE_DECISION.reason reports the intent_source, not the name of the guard that caused the downgrade; emitting the firing rule id turns the override rate into a per-rule rate for the next reduction pass.
  3. Prefer dbp:name over the entity id in grounded answers. The cup is answered as codex_probe_cup (entity id) instead of TITAS (dbp:name). A grounded_context projection nuance, not a routing bug; predates this refactor.
  4. turn_engine.py is still the largest module (1601 lines). The remaining structural target is the behaviour-changing merge of _resolve_planner_mode_turn and _lock_intent_first_route that Phase 1 deliberately left apart; needs its own gated pass.
  5. #6/#7 not explicit_route gating — deferred, not rejected. Live showed 0 wrongly-overridden execution turns (8/8 clean), so there was no harm to fix; revisit only if a future run shows an explicit execution route downgraded.
  6. Operational: KB service resilience across restarts. Aggressive process kills left stale FastRTPS shared-memory locks and duplicate knowledge_core nodes, making /kb/revise time out (one transient "I cannot confirm" cup answer). Prefer docker restart nao_ros2 over kill -9 loops. Not a chatbot defect.
  7. Bake the dedup into the image. The applied label change is live in nao_ros2 and in the host working tree; run build_docker.sh so the next iiia:nao image carries it permanently.
  8. Intent-first stays unpromoted. The _lock_intent_first_route mirror is an unscored ablation; do not make it the default.
  9. Update ISSUE_TRACKER_FULL_SUITE.html with the live Phase-2 results captured here.
