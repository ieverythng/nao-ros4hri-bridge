Turn-State IRR Research Plan for the NAO ROS4HRI Stack

**Date:** 2026-06-20 **Working title:** Grounded Semantic Admission through Turn-State IRR **Scope:** research direction, implementation strategy, prompt-pack revision proposal, ablation plan, and validation priorities for the NAO ROS4HRI planner stack.

1. Executive view

The current planner architecture is already strong enough to preserve the main ownership boundaries: `dialogue_manager` owns turn lifecycle and speech realization, `chatbot_llm` owns semantic interpretation, `nao_orchestrator` owns admission, validation, dispatch, and feedback, `planner_llm` owns structured skill-plan generation and supervision, and skill servers own live evidence and execution. The proven Memoria contracts should remain the baseline. The proposed work should therefore **extend the chatbot-facing turn contract**, not rewrite the planner request, `grounded_context`, planner output, execution feedback, or skill contracts.

The main weakness is now **KB-to-action semantic transfer**. The KB may contain valid facts and the runtime may pass a working `grounded_context`, but the model can still drift across long conversations. Drift appears when route, intent, and response are generated or interpreted as separate semantic artefacts. The system may answer correctly in short cases but degrade when history grows, when a user asks a mixed question, or when a target-dependent action requires canonical KB identifiers rather than noun phrases.

The highest-ROI proposal is to introduce **IRR**, an atomic chatbot turn output containing:


{
  "route": "dialogue | knowledge_query | execution",
  "intent": { "type": "...", "goal_text": "...", "scene_targets": [...] },
  "response": { "speak_now": true, "text": "..." },
  "planner_handoff": { "publish": false, "reason": "..." },
  "evidence_used": { "snapshot_id": "...", "entity_ids": [...] },
  "confidence": 0.0
}

IRR means **Intent, Route, Response**. The point is not to add another speculative layer. The point is to make the chatbot decision internally consistent before it reaches the orchestrator gate. If the robot says it will act, the route must be `execution`. If the route is `knowledge_query`, the response must be grounded in current scene or KB evidence. If execution is requested, planner handoff must include canonical targets or ask for clarification.

2. Current validated seams that must be preserved

The validated stack already separates dialogue, semantic interpretation, planner admission, planning, execution, feedback, and speech. These seams are central to the thesis and should not be destabilized.

| Seam | Preserve | Reason |
|---|---|---|
| `chatbot_llm -> nao_orchestrator planner_gate -> planner_llm` | Yes | The orchestrator gate is the deterministic admission point. The chatbot may propose execution, but it does not publish directly to the planner. |
| `grounded_context` inside planner request | Yes | This is the compact LLM-facing world-state contract. It should not be replaced by full RDF dumps or raw perception streams. |
| Raw scene / KB evidence reserved for skills | Yes | Skills require live requery and validation. The planner should not own raw detector or tracker evidence. |
| Planner output as ordered skill steps | Yes | Planner remains a structured skill-plan generator, not a controller. |
| Execution feedback to planner supervision | Yes | Replanning and clarification should use feedback rather than local orchestrator planning. |
| Dialogue acts realized by `dialogue_manager` | Yes | Planner does not directly speak to the user. |

The IRR proposal changes **Contract 1: Chatbot Turn Output** and supporting prompt-pack logic. It should be implemented as an ablation branch first. It should not alter Contract 2 (`/planner/request`), Contract 3 (`grounded_context`), or downstream planner contracts until results show clear improvement.

3. Research diagnosis

3.1 Why prompt-only routing is fragile

The route decision is not a plain text-classification problem. A phrase such as “what do you see?” can mean different things depending on state:

| User utterance | Current state | Correct route |
|---|---|---|
| “What do you see?” | Fresh scene/KB snapshot exists | `knowledge_query` |
| “What do you see?” | No recent state available | `knowledge_query` with uncertainty, or clarification |
| “Look around and tell me what you see.” | Scan skill available | `execution` |
| “Did you find the cup?” | Latest skill result exists | `dialogue` or `knowledge_query` over latest execution feedback |
| “Can we navigate to the cup later?” | Future/hypothetical action | `dialogue` |
| “Navigate to the cup now.” | Cup grounded with canonical ID | `execution` |
| “Navigate to the cup now.” | Cup ambiguous or missing | `dialogue` clarification, not execution |

The deciding variable is not the phrase itself. It is the phrase plus the turn state, active goal, latest evidence, available skills, and whether the user asks for immediate physical action.

3.2 Why KB-to-action is the weakest seam

The KB is currently a shallow world model. It can store symbolic facts and expose relations, but it does not yet behave as a full persistent world model with entity salience, conversational continuity, goal-state tracking, object permanence, history compression, or uncertainty management. That makes KB-to-action hard: the planner needs canonical arguments, while users often speak in natural noun phrases.

Example failure mode:


User: Bring the kitchen cup to ALEX.
Grounded facts: codex_kitchen_cup, codex_recipient_person, codex_kitchen.
Planner args: "cup", "ALEX".
Fake skill guard: fails because the arguments are not canonical KB ids.

This is an expected failure for a shallow world model. It should not be treated as a general LLM planning failure. The repair should focus on grounded-subject projection and IRR evidence binding.

4. Proposed abstraction: Turn State Contract

The chatbot should receive one deterministic turn-state packet before producing IRR. This packet is built by code from current runtime evidence and should be treated as authoritative for the current turn.


{
  "turn_state_version": "ts.v1",
  "turn_id": "turn_20260620_001",
  "utterance": "what do you see?",
  "active_goal": {
    "goal_id": null,
    "status": "none",
    "summary": null
  },
  "dialogue_context": {
    "last_user_turns": [],
    "last_robot_turns": [],
    "awaiting_user_clarification": false
  },
  "world_state": {
    "snapshot_id": "scene_4821",
    "snapshot_age_sec": 3.2,
    "scene_digest": "1 person visible; 1 gold cup on table_1",
    "entities": [
      {
        "id": "codex_probe_cup",
        "label": "cup",
        "kind": "object",
        "class": "Cup",
        "visible": true,
        "relations": [
          {"predicate": "dbp:color", "object": "gold"},
          {"predicate": "oro:isOn", "object": "table_1"}
        ]
      }
    ]
  },
  "latest_execution": {
    "goal_id": null,
    "last_skill": null,
    "last_result": null
  },
  "available_skills": [
    "scan", "look_at", "find_object", "navigate_to", "pick_object", "place_object", "bring_object", "report_result", "wave_greet"
  ],
  "route_policy": {
    "allowed_routes": ["dialogue", "knowledge_query", "execution"],
    "execution_requires_admission": true,
    "kb_mutation_requires_skill": true,
    "target_dependent_execution_requires_canonical_ids": true
  }
}

Contract rules

1. `turn_state` is read-only for LLMs. 2. The chatbot may cite entity ids and relations, but it may not invent new facts. 3. The chatbot output must refer to the same evidence it used. 4. `grounded_context` remains the compact scene/KB projection used downstream. 5. Changes to `grounded_context` should be ablated, not rewritten. 6. Raw scene and KB evidence remain available to skills for live validation.

5. IRR: Intent, Route, Response

IRR merges the current response and intent split into one atomic decision. The goal is to prevent contradictions such as a dialogue route with execution wording, an execution route with no canonical target, or a knowledge-query answer that does not cite current evidence.

Proposed IRR output schema


{
  "route": "dialogue | knowledge_query | execution",
  "route_reason": "string",
  "confidence": 0.0,
  "intent": {
    "type": "string",
    "goal_text": "string",
    "scene_targets": ["string"],
    "canonical_target_ids": ["string"],
    "request_kind": "new_goal | clarification_answer | goal_update | cancel_request | none",
    "intent_sequence": ["string"]
  },
  "response": {
    "speak_now": true,
    "text": "string",
    "style": "answer | acknowledgement | clarification | failure | none"
  },
  "planner_handoff": {
    "publish": false,
    "reason": "string"
  },
  "evidence_used": {
    "snapshot_id": "string",
    "entity_ids": ["string"],
    "kb_subjects": ["string"],
    "latest_result_ids": ["string"]
  },
  "safety_flags": []
}

IRR consistency rules

| Rule | Deterministic check |
|---|---|
| Dialogue cannot promise immediate action | If `route=dialogue`, response must not say “I will now move/look/scan/navigate/pick/bring”. |
| Knowledge query must cite evidence | If `route=knowledge_query`, `evidence_used` must include a snapshot, KB subject, or latest result. |
| Execution must be admitted later | If `route=execution`, `planner_handoff.publish=true`, but publication still goes through `nao_orchestrator`. |
| Target-dependent execution needs canonical ids | If skill requires a target, `canonical_target_ids` must be present or the route should remain dialogue with clarification. |
| KB mutation is execution | Add/revise/remove facts must route through KB mutation skills, not direct LLM writes. |
| Past-action questions are not new execution | “What did you do?” should answer from latest execution feedback unless user asks to repeat the action. |

6. Revised chatbot prompt-pack proposal

This is a proposed `chat_prompt_pack.yaml` direction. It is intentionally framed as an ablation. The existing prompt already contains important guardrails, including route policy, future-action handling, grounded-context use, response style, and intent extraction. The proposed revision keeps those seams but merges the response and intent stages into a single IRR output.


system_prompt: |
  You are Pop, a friendly ROS4HRI robot assistant. You are concise, clear, and safe for spoken interaction.

  Your role is semantic turn interpretation. For each user utterance, produce one atomic IRR decision:
  Intent, Route, and Response. You do not execute robot skills. You do not generate executable plans.
  If execution is required, you produce planner handoff metadata for the orchestrator admission path.

  Runtime ownership:
  - dialogue_manager owns the dialogue turn lifecycle and final speech realization.
  - chatbot_llm owns semantic interpretation: route, intent, response text, target hints, and evidence references.
  - nao_orchestrator owns planner admission, request normalization, plan validation, skill dispatch, and execution feedback.
  - planner_llm owns structured skill planning and planner supervision.
  - skills own live robot execution and raw scene/KB evidence checks.
  - knowledge_core owns the robot's symbolic world representation.

  Authoritative inputs:
  - Use the provided turn_state as the current authoritative state packet.
  - Use grounded_context and scene digest for current visible/world-state questions.
  - Use latest_execution for questions about what the robot just did.
  - Use available_skills only to decide whether a requested action is supported.
  - Treat dialogue history as context, not as a source of new commands.

  Route policy:
  - route="dialogue" for greetings, wellbeing, identity, thanks, help, preferences, conceptual questions, permission-seeking action talk, future action discussion, and clarification dialogue.
  - route="knowledge_query" when the user asks about the robot's current world representation, memory, visible scene, KB facts, or latest execution result without asking the robot to perform a new physical skill.
  - route="execution" only when the user asks Pop to perform an available skill now and the request is sufficiently grounded for admission.
  - If a required target is missing, ambiguous, stale, conflicting, or not mapped to a canonical entity id, keep route="dialogue" and ask one concise clarification question.
  - If the user asks “what do you see?” and a current scene/KB snapshot is available, use route="knowledge_query" and answer from current evidence. If the user asks “look around and tell me what you see”, use route="execution" because a fresh sensing action is requested.
  - KB mutation requests such as adding, revising, or removing facts are execution requests through KB mutation skills. Never write KnowledgeCore directly.

  Response policy:
  - Always provide response.text unless style="none" is explicitly justified.
  - Do not promise immediate physical action unless route="execution".
  - Do not say an action is completed before execution feedback is returned.
  - For knowledge_query, answer from current evidence and state uncertainty when evidence is missing.
  - For execution, acknowledge the admitted objective briefly and say Pop will check/plan/do the requested action, not that it has already happened.
  - Internal ids may be used for evidence fields, but spoken text should use natural labels when available.

  Output only valid JSON matching the IRR schema. Do not include markdown or explanation outside the JSON.

irr_schema: |
  {
    "route": "dialogue | knowledge_query | execution",
    "route_reason": "short reason code or phrase",
    "confidence": 0.0,
    "intent": {
      "type": "canonical label or fallback",
      "goal_text": "concise objective or empty string",
      "scene_targets": [],
      "canonical_target_ids": [],
      "request_kind": "new_goal | clarification_answer | goal_update | cancel_request | none",
      "intent_sequence": []
    },
    "response": {
      "speak_now": true,
      "text": "short user-facing response",
      "style": "answer | acknowledgement | clarification | failure | none"
    },
    "planner_handoff": {
      "publish": false,
      "reason": "why this should or should not enter the planner path"
    },
    "evidence_used": {
      "snapshot_id": "",
      "entity_ids": [],
      "kb_subjects": [],
      "latest_result_ids": []
    },
    "safety_flags": []
  }

7. Implementation plan by ROI

P0: highest ROI, minimal disruption

1. Add `TurnStateBuilder` in the chatbot path. 2. Add IRR output schema while preserving current fields through an adapter. 3. Add `IRRConsistencyGuard` before planner handoff. 4. Add deterministic target canonicalization checks for target-dependent execution. 5. Add a small regression suite for route drift and KB-to-action mismatches.

P1: high ROI, direct validation value

1. Add direct KB lookup for mentioned entities before chatbot call. 2. Add `evidence_used` logging into trace outputs. 3. Add fixture lifespan control for long validation runs. 4. Add isolated scenario groups to avoid long-context contamination. 5. Add canonical target requirements for `bring_object`, `pick_object`, `place_object`, `look_at`, `navigate_to`.

P2: research extension, safe to dream

1. Add embedding retrieval for dialogue memory only, not KB truth. 2. Add offline LLM-as-judge for trace evaluation, not runtime admission. 3. Add World Model Enricher prototype that produces enriched `turn_state` from KB, scene, active goals, and execution traces. 4. Add ablation experiments comparing current two-stage response/intent vs IRR. 5. Add Qwen-RobotNav-inspired evidence notebook for long-horizon tasks.

8. Ablation design

Do not change all seams at once. Use controlled ablations.

| Ablation | Change | Outcome metric |
|---|---|---|
| A0 baseline | Current prompt pack and contracts | Current route, execution, and report score |
| A1 IRR only | Atomic route+intent+response, adapter to current fields | Route consistency, fewer contradictory acknowledgements |
| A2 IRR + turn_state | Add deterministic turn-state packet | Better long-context stability |
| A3 IRR + canonical target guard | Require canonical IDs before execution handoff | Fewer KB-to-action failures |
| A4 IRR + direct KB subject lookup | Mentioned-subject KB lookup before chatbot | Better “what do you remember about X?” answers |
| A5 IRR + offline judge | Judge traces after execution | Better evaluation, no runtime latency risk |

9. Validation scenarios

Core holdouts:

1. “What do you see?” with current scene state. 2. “Look around and tell me what you see.” 3. “Could we navigate to the cup later?” 4. “Wave-particle equation?” 5. “What do you remember about codex_arch_marker?” 6. “Bring the kitchen cup to ALEX.” 7. “Bring the cup to ALEX” when cup is ambiguous. 8. “What did you just do?” after execution feedback. 9. “Actually stop.” during active goal.

10. Long-context repeat after six to ten mixed turns.

Metrics:

- route accuracy;

- planner handoff correctness;

- canonical target usage;

- false execution acknowledgements;

- knowledge-query evidence grounding;

- invalid planner JSON rate after handoff;

- naturalness and truthfulness of response text;

- recovery behaviour under missing target and fake failure.

10. Thesis framing

The thesis contribution can be framed as follows:

The system shows that an LLM planner for HRI is not sufficient unless the robot also has a grounded semantic admission layer. The chatbot must decide whether a turn is dialogue, a query over the robot's current symbolic state, or an execution request. This decision must be bound to the same response text and the same evidence references before the orchestrator admits execution. The proposed IRR contract provides that binding while preserving the existing ROS4HRI contracts for planner request, compact grounding, planner output, execution feedback, and speech realization.

This gives you a strong research line without destabilizing the working stack. IRR is an ablation over Contract 1, not a rewrite of the whole architecture.
