Prompt Pack Hardening Plan (ROS4HRI Harness)

Last updated: 2026-05-09 | Scope: chatbot_llm, planner_llm, prompt ingestion, validation, rollout safety

This plan consolidates a deeper audit of current prompt assembly and runtime behavior, then proposes a phased implementation to align chatbot/planner prompt pipelines for better reliability, easier tuning, and faster experiment cycles.

Primary finding: prompt ingestion is currently asymmetric. chatbot_llm has a YAML prompt-pack pipeline with fallback merge semantics; planner_llm still embeds its system contract in Python constants plus inline retry copy.

2) Current Design: Strengths and Friction

Area Current Strength Current Friction / Risk
Chatbot prompt ingestion Human-editable YAML pack + safe fallback defaults. Dual override paths (prompt_pack_path and raw ROS params) can drift across deployments.
Planner prompt ingestion Strong in-code contract checks and tests. Prompt prose lives in code constants; slower operator iteration and weaker config traceability.
Capability grounding skill_registry.json + prompt_manifest() keep capability data structured. No prompt-pack layer for planner policy text to evolve independently from Python edits.
Performance guardrails Preflight probes, small token limits for chatbot turns, no-think guards for qwen models. Prompt complexity and verbosity are not explicitly budgeted per stage; no stable prompt version id in runtime logs.

3) Performance Signals To Improve

  • Planner output reliability still depends on prompt phrasing details in planner_engine.py.
  • Cross-model behavior (Ollama/OpenAI-compatible) differs, while prompts are not versioned per provider profile.
  • Chatbot response and intent phases share common context but do not expose an explicit prompt revision stamp in telemetry.
  • Prompt edits currently require mixed edit locations (YAML, ROS params, Python constants), which increases rollout mistakes.

4) Target Prompt Architecture

4.1 Prompt Pack Symmetry

  • Add planner_llm/config/planner_prompt_pack.yaml.
  • Add planner_llm/prompt_pack.py mirroring chatbot semantics: default_prompt_pack(), load_prompt_pack(path), parse fallback, partial override merge.
  • Add ROS param planner_prompt_pack_path with empty-path auto-resolution to install/share path.

4.2 Layer Separation

  • Layer A (policy prose): YAML pack (model-facing natural language).
  • Layer B (hard contract rules): Python validation logic + tests (must stay code-enforced).
  • Layer C (capability surface): skill_registry.json + prompt manifest (data-only).

4.3 Prompt Versioning

  • Add optional prompt_pack_version field in both packs.
  • Emit version in startup/preflight logs and planner request traces.

5) Implementation Plan (Phased)

Phase A — Non-breaking Scaffolding

  1. Create planner prompt-pack loader and default YAML file.
  2. Keep existing _SYSTEM_PROMPT as fallback to preserve behavior.
  3. Add unit tests for empty path, bad YAML fallback, and partial override merge.

Phase B — Controlled Migration

  1. Move planner system prose and retry guidance text into the YAML pack keys.
  2. Retain hard validity checks in Python (step type/name enforcement, required fields).
  3. Add regression tests for existing invalid-plan and retry behavior.

Phase C — Experiment Harness

  1. Add profile-specific prompt packs (e.g., demo, lab-vllm, robot-safe).
  2. Add a small prompt-eval script that replays fixed planner fixtures and reports pass/fail latency.
  3. Track prompt version in benchmark outputs.

Phase D — Runtime Hardening

  1. Add explicit length budgets for system prompt sections to reduce overflow/noise risk.
  2. Add mandatory “contract guard” section in planner prompt pack to avoid accidental weakening.
  3. Add change checklist: prompt edit must include test update or explicit rationale.

6) Prompt Quality Hardening Checklist

  • Use deterministic verbs and avoid ambiguous synonyms for contract fields.
  • Separate “must” constraints from “style” hints in distinct blocks.
  • Keep completion wording ownership explicit: planner decides structure, chatbot/dialogue own user-facing phrasing.
  • Avoid embedding robot-specific transport details in model prose when contract already encodes them.
  • Guard against chain-of-thought leakage via provider-level no-think controls and output schema checks.
