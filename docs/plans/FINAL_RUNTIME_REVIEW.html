What Might Still Be Missing

  • Intent-first response wording: route lock avoided false execution for favourite-movie and wave-particle questions, but the response text incorrectly said it could not provide information. This is the most visible current ablation regression.
  • Action plus report in intent-first: “Look at the probe cup and tell me what you did” was misclassified as a knowledge query in one live trace. It needs a route-lock conflict gate before intent-first can be a candidate default.
  • Full rqt speech KB mutation: add/revise/remove are service-path proven, but the final report should still keep a speech-mode add/revise/query/remove gate where the prompts enter through the same rqt/ROS4HRI path as supervisor interaction.
  • Manual KB add format: explicit RDF-like statements such as codex_arch_marker rdf:type Cube pass. Vague requests such as “add one cup” are currently admitted as kb_add, then fail because the planner emits prose as a KnowledgeCore statement. The desired behavior is clarification: ask for name, type, color, and relation instead of executing an invalid mutation.
  • Location-scoped grouped delivery: source now supports grouped location context and a late planner fallback, but the live proof still needs the exact “bring every object from the kitchen to ALEX” flow with canonical object and recipient ids.
  • Skill-aware KB effects: source now applies successful fake-skill KB effects through the orchestrator, but the next run must prove a post-skill KB state change through query and chatbot response.
  • Preloaded environment fixtures: table inventory is now speech-proven with deterministic KB fixture insertion. The full fixture ladder still needs grouped delivery and post-effect follow-up without harness interruption.
  • Direct subject recall: latest response-first architecture evidence now answers “What do you remember about codex_arch_marker?” from the injected type, name, and color facts. Keep it as a holdout because older runs were safe but under-informative.
  • Fixture-isolated recovery: the final absent-cup prompt found an existing kitchen-cup fixture, so it does not prove missing-target fallback. Rerun recovery with no matching cup facts or with a deliberately absent id.
  • Failure/fail-once speech paths: direct fake-skill failures are proven, but chatbot/planner speech turns still need absent object, absent recipient, delivery blocked, unreachable, and fail-once variants.
  • Delivery wording: the prior “placed the cup on Alex” wording is fixed in the final live detector-profile run. Keep the table-placement holdout so ordinary “placed it on the table” wording is not overcorrected.
  • Spatial/proximity validation: publish one trusted simulator pose overlay and verify scene summary, KB statements, grounded context, and a proximity answer.
  • Long-history stress: repeat the accepted holdouts after dialogue history exceeds the configured trim threshold. If degradation returns, add a careful conversation-revision seam that excludes grounded-context snapshots.

Deep Fake And Replan Validation

This section is the supervisor-facing summary of the new fake-skill validation layer. The main runtime matrix still answers whether the whole stack can speak, query KB, plan, execute, and report. The fake suite asks a harder question: when the world is virtual but semantically precise, can the robot use grounded RDF objects, recover from fake failures, and avoid false completion?

Validation layerWhat is preloadedQuestions usedAcceptance condition
Baseline scenebaseline_table: robot station, one table, red cup, blue book.“What objects are on the table?”Grounded context and speech agree on the visible table objects before any execution case starts.
Ordered report chainlab_table: multiple table objects with stable names, colors, and support relations.“Walk to every object on the table and let me know when you get to each one.”Planner expands the object set, executes ordered navigation, and reports each arrival once.
Grouped deliverylab_sections: work table, desk, computer objects, cup, book, phone, and ALEX in a handoff area.“Bring every object from the work table to ALEX and report what happened.”Location relations are converted into concrete object ids and delivered to the named person with an explicit recipient location.
Absent target recoverybaseline_table without the requested missing cup.“Find the codex missing cup. If you cannot find it, scan the scene and report what you can confirm.”The stack replans to scan/report or fails truthfully. It must not claim the missing cup was found.
Missing recipientlab_sections with ALEX present but no BLAKE.“Bring every object from the work table to the person named BLAKE and report what happened.”The system clarifies, asks for help, or fails safely without inventing a recipient.
Maximal environmentiiia_floor: lab, kitchen, corridor, robot station, handoff area, ALEX, and distributed objects.“Bring every object from the kitchen to ALEX and report what happened.”Multi-location planning uses canonical kitchen objects, recipient location context, and post-skill KB effects.
Multi-turn handoffgold_apple_handoff: a gold apple and human recipient in a handoff area.“Can you bring that gold apple to the person named ALEX?” then “Where is the gold apple now?”The follow-up answer comes from the updated KB state after delivery.

The method follows scenario-based robot validation practice: each case has an explicit environment, task, variation condition, expected evidence chain, and pass/fail rule. The corresponding executable route is run_active_questionnaire.py --case-set fake_deep --fake-policy-profile .... Profiles such as fail_once_navigation, fail_once_pick, delivery_blocked, and recipient_missing are used to force replanning or truthful failure in a controlled way.
