Dialogue and execution admission

  • Use dialogue to discuss and refine possible future execution goals.
  • Before execution handoff, identify the complete requested outcome, required targets, relevant grounded predicates, and matching skills.
  • When world state conflicts with the request or required information is missing, ask one concise clarification question.
  • Do not emit a future-tense execution acknowledgement until the request is admitted.
  • Preserve the seam chatbot_llm -> nao_orchestrator planner gate -> planner_llm.

Planning and execution

  • Planner arguments should use grounded entity identifiers and RDF relations where available instead of relying only on phrases such as “red cup”.
  • The ordered steps list defines execution order. requires identifies prior steps whose success or evidence is needed by a later step.
  • Fake skills should enforce real grounded targets or define explicit scenario-owned KB objects and mutations.
  • Execution failures must support safe replanning, clarification, help requests, or terminal failure according to the plan contract.

User-facing completion

  • Planner dialogue acts, report results, clarifications, failures, and completion wording must use chatbot with its canonical system prompt and relevant dialogue, goal, grounding, plan, and execution evidence.
  • report_result must summarize the complete relevant skill chain naturally.
  • A report-result wording failure must not crash the execution stack. A bounded safe fallback remains available.
  • Internal entity identifiers, raw planner text, JSON, and policy fields must not leak into speech.

Grounding and perception

  • Stable interaction-sim and KnowledgeCore objects are the primary grounding acceptance probe.
  • Detector-derived facts require a confidence score of at least 0.70 in the active launch defaults.
  • Prompt and projection logic must prioritize entity identifiers, semantic classes, and relations.
  • Runtime reviews must distinguish missing KB facts from facts present in grounded context but ignored by the model.

Semi-symbolic incoming seams

These items are consolidated from semi_symbolic_requirements_handoff_2026-06-11.html. They are expected to arrive in a near-term commit and should be validated against the same runtime review gates before submission.

  • Explicit KB mutation: support guarded add, revise, and remove fact requests through chatbot intent admission and orchestrator-owned KB skill dispatch. LLM nodes must not write KnowledgeCore directly.
  • Non-mutating KB dialogue: ordinary questions about facts, visibility, names, colors, and relations must not revise KB state.
  • Frame-qualified object positions: simulator or 3D pose producers may provide positions keyed by entity id, frame id, and timestamp. 2D image detections must not be converted into metric locations without a trustworthy pose source.
  • Spatial relations and proximity: distance, near/far, left/right, and support predicates should be derived only from explicit spatial evidence and exposed through grounded context.
  • Human-inclusive reporting: mixed scene summaries must preserve people and objects as separate entity kinds.
  • Validation artifacts: runtime reviews should preserve JSON, CSV, and HTML evidence for the TFM where possible, not only screenshots or prose summaries.
