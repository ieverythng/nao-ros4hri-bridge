Validation Method

PrincipleHow it is applied hereWhy it matters
Scenario modelEach run declares an environment fixture, task prompt, fake policy profile, expected post-condition, and trace artifacts.Scenario-based robot validation literature emphasizes explicit operating context, task, variation conditions, and acceptance criteria so failures are reproducible rather than anecdotal.
Configurable launch surfacepreloaded_environment_ids:=... initializes the sim stack with a stable semantic scene. The questionnaire can override this per run with --preload-environment or per case through environment_ids.ROS 2 launch arguments and parameters are the right seam for repeatable runtime variation. They avoid hidden code edits and make supervisor demos repeatable.
Evidence chainEvery pass must show /kb/revise, /kb/query, grounded context, planner request, fake feedback, execution feedback, and speech outcome when applicable.This separates “fact never existed” from “fact existed but the model ignored it” and from “execution failed but was reported incorrectly.”
Difficulty ladderStart with inventory, then single action, composite action, grouped location delivery, multi-turn pronoun handoff, and finally forced failure/replan.The tests become harder in controlled steps, similar to puzzle-room validation: each scenario isolates one new semantic demand before combining several.

Artifact Contract

ArtifactRequired fieldsPass condition
Questionnaire JSONruntime_metadata.fake_policy_profile, environment_fixture_source, case setup_result.environment, per-case logs, and speech/trace samples when enabled.The artifact proves which scenario and fake policy were active for every case.
Phase observationsPer-case phase_observations.turn_injected, route_observed, planner_request_observed, execution_feedback_observed, terminal_observed, and speech_observed, refreshed during long waits. The runner only short-circuits a case after both terminal and speech evidence are present.A failure can be assigned to ingress, route, planner handoff, execution, terminal policy, or speech instead of looking like a generic hang.
Stale-world guardPer-case stale_world_guard.contaminated, query patterns, row counts, and raw /kb/query evidence for absent-target cases.Missing-object and missing-recipient tests are skipped as contaminated when stale KnowledgeCore facts already match the target before the user turn.
Plan outcome summarycompleted_targets, failed_targets, pending_targets, last_successful_step_id, terminal_step_id, terminal_reason, and all_required_steps_succeeded.Report-result wording has structured executor evidence and must not claim all required targets succeeded when pending or failed targets remain.
KB evidence/kb/revise result, /kb/query confirmation, and post-action query for effects.Post-conditions match the expected object, holder, location, or absence state.
Planning evidence/planner/request, executable plan JSON, /planner/execution_feedback, and replan/failure dialogue act.Planner uses canonical ids and either recovers or fails truthfully.
Speech evidence/debug/nao_say/speech or dialogue-manager speech output plus exactly-once trace.One semantic event produces one user-facing utterance. No raw planner text or false completion.
Operator SVGScene map opened from preloaded_environment_viewer.html or ros2 run nao_chatbot preloaded_environment_viewer --open.Human reviewer can visually identify the fixture being tested during rqt operation.
